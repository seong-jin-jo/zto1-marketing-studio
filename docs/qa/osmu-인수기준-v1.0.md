# OSMU 인수 기준과 QA 시나리오 v1.0

## 이 문서가 있는 이유

지금까지 인수 기준을 승인된 기획서에서 뽑지 않고 회장이 그 자리에서 지적한 것으로 삼았다.
그래서 카드뉴스·영상·취소·리셋·학습 정보 완료·작업물 목록 축이 통째로 비었고, 회장 스모크
한 번에 일곱 건이 쏟아졌다. 이 문서는 그 재발을 막기 위해 **기획 정본에서 인수 기준을
끌어와** 고정한다. 새 판은 이 표를 통과해야 완료다.

## 근거가 되는 기획 조항

| 조항 | 무엇을 정했나 |
|---|---|
| 사업계획 v0.4 §10 | 첫 매체는 카드뉴스. 만들기 전 비용 승인 관문을 둔다 |
| 사업계획 v0.4 §7 | 원가는 생성 호출에서 난다. 실측 건당 5에서 95 크레딧 |
| PRD v8.2.1 §도입부 | 고객이 저해상도 후보 3개를 받아 1개만 고해상도로 완성한다 |
| studio 계약 v3 | 만들기 전 estimate, 승인 상한과 함께 production 생성 |
| ADR-006 | 심사 전 한시 절차는 화면이 링크까지 준다. 연결 단추를 막지 않는다 |
| ADR-007 | 조용한 실패 금지. 못 하면 이유를 말하고 빠져나갈 길을 준다 |

## 2026-09-08 밤샘 검증 — 무엇이 서고 무엇이 안 서는가

### 실계정에서 눈으로 확인한 것

| 항목 | 확인 방법 | 결과 |
|---|---|---|
| 전 구간 관통 | 새로 시작 → 주제 입력 → 초안 생성 → Threads 발행 → 프로필 확인 → 성과실 | 통과. 게시물 `post/Dc_5uomk_56` |
| 카드뉴스 이미지 생성 | 생성실 단추 | 1536×1536 |
| 숏폼 영상 생성 | 생성실 단추 | 768×768, 5.9초 |
| 만들기 전 결 고르기 | 카드 6종 + 직접 적기 | 화면 노출·결과 반영 |
| 브랜드 색이 그림에 반영 | 학습 정보 팔레트 | 올리브 그린·크림으로 생성 |
| 그림 속 글자 없음 | 같은 주제 3회 비교 | 제거 확인 |
| 편집실이 산출물 표시 | 생성 직후 편집실 이동 | 1536px 표시 |

| 학습 정보 서버 보관 | 브라우저 저장소 삭제 후 새로고침 | 6/7 유지 |
| 유튜브 연결 | OAuth 완주 | 연결됨 (투자자J) |

### 오늘 고친 결함 (전부 실사용에서 나옴)

1. 배포가 생성기 로그인을 옛 스냅샷으로 덮어써 죽이던 것
2. 토큰 갱신값을 보관만 하고 쓰지 않던 것 (하루 몇 번씩 재연결 요구)
3. 갱신을 넣으며 만료 관문을 잃은 회귀 (내가 만든 것)
4. 성과에서 배운 규칙이 생성에 반영되지 않던 것
5. 학습 정보가 브라우저에만 있어 기기를 바꾸면 사라지던 것
6. 첫 사용 안내가 고객에게 한 번도 안 뜨던 것 (3중)
7. 편집실이 산출물 주소를 못 받던 것 (3중)
8. 산출물 배달 주소 수명이 15분이라 정상 사용에서 반드시 만료되던 것
9. 발행 오류를 502로 답해 프록시가 문구를 삼키던 것 (영상 발행·이미지 생성 두 곳)
10. 그림 지시문에 카드뉴스 본문이 들어가 글자가 그려지던 것
11. 한도 정리 단추가 수학적으로 통과 불가능하던 것
12. 배포가 레포 개명으로 죽던 것
13. 링크드인 발행 기능 부재 (마지막 미구현 채널)

### 안 서는 것과 그 이유

| 채널 | 막는 것 | 누가 풀 수 있나 |
|---|---|---|
| Instagram | Instagram 전용 앱 시크릿 확인. Meta 가 비밀번호 재인증 요구 | 회장만 |
| Facebook | 관리 중인 페이지 없음. 생성 화면 카테고리 선택을 자동화가 통과 못 함(4회 시도) | 회장만 |
| X 발행 | 사용 요금 소진 | 회장만 (돈) |
| TikTok | 앱 등록. 가입에 메일 인증 번호 필요 | 회장만 |
| LinkedIn | 앱 등록 | 회장 |

**즉 남은 것은 코드 문제가 아니다.** 발행 기능이 없는 채널은 이제 없고, 전부 계정·권한·결제에서 막혀 있다.

### 오늘 내가 낸 오진 세 건 (같은 원인)

1. 어제 게시물 주소를 오늘 발행 결과로 읽음
2. 다른 지시문으로 비교해 재생성이 고장 났다고 판단
3. 알림이 그려지는 자리를 몰라 발행이 무반응이라고 판단

셋 다 **관측 조건을 확인하지 않고 결론부터 낸 것**이다. 다음 세션은 판정 전에 "내가 보는 자리가 맞는가, 비교 조건이 같은가" 를 먼저 확인한다.

## 유튜브: 네 겹이었다 (2026-09-07)

회장이 "회원가입 할 때마다 개발자 센터에 들어가야 하냐"고 지적한 뒤 접근을 바꿔 크롬으로
직접 밀었다. 막고 있던 것이 하나가 아니라 **네 겹**이었고, 하나를 풀 때마다 다음 문구가
나왔다. 앞의 겹을 풀지 않으면 뒤의 겹은 보이지도 않는다.

| 겹 | 증상 | 원인 | 조치 |
|---|---|---|---|
| 1 | 콘솔의 모든 변경이 저장 거부(테스트 사용자 추가 6회 실패) | 브랜딩에 홈페이지·개인정보처리방침·약관 주소가 비어 "OAuth 구성 미완료" 상태 | 세 주소를 채우고 저장. "브랜딩 변경사항이 저장되었습니다" 확인 |
| 2 | 테스트 사용자만 접근 가능 | 앱이 테스트 중 | **앱 게시**로 프로덕션 전환. "프로덕션 단계" 확인 |
| 3 | 동의 통과 뒤 `The provided client secret is invalid` | 서버가 가진 시크릿이 콘솔 값과 다름 | 새 시크릿 발급, 저장소 시크릿 교체 |
| 4 | 시크릿을 갈았는데 같은 오류가 계속 | **자격증명은 DB 저장분이 환경변수보다 우선.** 서버가 DB 의 옛 값을 보고 있었고 어디에도 그 사실이 드러나지 않았다 | 배포에 덮어쓰기 단계를 넣어 지정한 제공자만 환경변수 값으로 갱신. HTTP 200 확인 |

**네 겹을 다 풀자 오류가 바뀌었다.** 이제 토큰 교환은 통과하고
`youtube 계정 신원 검증에 실패했습니다` 에서 멈춘다. 즉 인증은 끝났고 채널 조회 단계다.
YouTube Data API v3 는 이 프로젝트에서 이미 사용 설정돼 있다(콘솔 실측). 남은 유력한
원인은 **그 구글 계정에 유튜브 채널이 없는 것**이다. 채널이 없으면 조회가 빈 목록을 준다.

**4번은 이 저장소의 구조적 함정이다.** 콘솔에서 시크릿을 갈아도 배포가 따라가지 않는다.
같은 함정이 X·인스타그램에도 그대로 있다. 그래서 배포 입력 하나로 제공자를 지정해 갱신할
수 있게 만들었다. 앞으로 어느 채널이든 콘솔에서 값을 바꾸면 배포에 그 제공자만 적어
돌리면 된다.

## 인스타그램: 진짜 문구를 잡았고 경로 문제로 좁혔다 (2026-09-07)

동의 화면까지 눌러 마지막 단계에 도달해서야 처음으로 실제 오류를 봤다. 그동안은
"장기 토큰 실패" 라는 우리 말만 있었고 제공자가 뭐라 했는지는 몰랐다.

| 시도 | Meta 응답 |
|---|---|
| 버전 없는 GET (문서 기본) | `Unsupported request - method type: get` (HTTP 400) |
| 버전 붙인 GET | 같은 문구 |
| 버전 붙인 POST | `Unsupported request - method type: post` (HTTP 400) |

**더미 토큰으로 경로를 따로 재현해 원인을 좁혔다.** 아무 토큰이나 넣고 같은 경로를 부르면
`Invalid OAuth access token`(190)이 온다. 즉 **경로는 살아 있다.** 그런데 진짜 토큰을 넣으면
`Unsupported request` 가 온다. 토큰은 읽혔는데 **그 토큰의 앱 종류에는 이 경로가 없다**는
뜻이다. 동의 화면 흐름값이 `ig_biz_login_oauth` 인 것과 맞물린다.

그래서 첫 경로가 그 사유로 막히면 Facebook 쪽 교환으로 한 번 더 시도하도록 고쳤다.
**그것도 같은 사유로 막혔다.** 코드가 할 수 있는 두 길이 모두 닫혀 있으므로 남은 것은
Meta 앱 설정이다. 이 앱에 Instagram 관련 제품이 붙어 있는지, 어느 로그인 방식으로
구성됐는지를 콘솔에서 봐야 한다.

문서화된 기본 경로로 되돌리고 경로와 방식을 환경변수(`IG_LONG_TOKEN_URL`,
`IG_LONG_TOKEN_METHOD`)로 바꿀 수 있게 뒀다. **다음 시도는 코드 수정 없이 배포 설정만으로
가능하다.**

회장 조치: Meta 개발자 콘솔에서 이 앱이 Instagram Login 인지 Facebook Login 연동인지
확인해 주시면 경로를 확정한다.

## X 채널 관통 (2026-09-07)

회장이 "권한은 모두 승인한다" 고 하셔서 동의 화면까지 세션이 진행했다. 그 과정에서
**연결과 발행이 서로 다른 인증을 보고 있던 결함 두 개**가 드러났다.

| 단계 | 실제 오류 문구 | 원인 | 조치 |
|---|---|---|---|
| 토큰 교환 | `Missing valid authorization header` | X 는 기밀 클라이언트 토큰 교환에 HTTP Basic 을 요구하는데 본문에 열쇠만 실었다 | Basic 헤더를 함께 보낸다 |
| 발행 | `X 4키(apiKey/apiSecret/accessToken/accessSecret) 누락` | 화면 연결은 OAuth 2.0 토큰을 저장하는데 발행은 OAuth 1.0a 4키만 받았다 | v2 tweets 를 OAuth 2.0 사용자 토큰으로 올린다 |
| 발행 | `{"detail":"credits depleted","status":402}` | X API 사용 요금 소진 | 제공자 JSON 대신 사람 말로 가른다 |

**결과.** 연결 `x=connected`, 인증 통과, 발행은 **요금 소진으로 막힘**. 이것은 제품 결함이
아니라 X 요금 문제이고 돈이 나가는 결정이라 세션이 충전하지 않는다. 화면은 이제 이렇게
말한다.

> X 사용 요금이 소진돼 올리지 못했습니다. X 개발자 콘솔에서 크레딧을 채우면 바로 올라갑니다.

**두 결함은 고객이 연결까지 마쳐도 발행이 안 되게 만드는 것이었다.** 회장 계정으로
동의까지 눌러 보지 않았으면 둘 다 못 찾았다. 연결 진입이 302 로 열린다는 것과 실제로
올라간다는 것 사이에 두 칸이 더 있었다.

## 발행 계약 실검증 (2026-09-07)

| 번호 | 기준 | 실측 |
|---|---|---|
| P-1 | 발행이 성공으로 닫히고 게시물 주소를 준다 | **통과.** 100% 발행 완료, `threads.com/@j.the.great.investor/post/Dc6W0HOmBGr` 응답 200 |
| P-2 | 같은 작업물을 두 번 올리지 않는다 | **통과.** 같은 작업물로 다시 눌렀더니 새 글이 생기지 않고 같은 글을 가리켰다 |
| P-3 | 연결이 끊긴 채널은 대상에서 빠지고 다시 연결 길을 준다 | **통과.** 인스타그램 토큰 취소 상태에서 "올릴 수 없는 1곳 제외" 로 빠지고 재연결 안내가 뜬다 |

**채널 범위의 한계를 정직하게 적는다.** 지금 이 작업 공간에 실제로 연결된 채널은 Threads
하나다(인스타그램은 토큰이 취소됨). 나머지는 연결 자체가 회장 동의 클릭을 필요로 하고
동의 화면은 세션이 대신 누를 수 없다. 그래서 **발행 계약은 Threads 로 검증했고 다른
채널은 미검증**이다. 채널마다 API 가 다르므로 Threads 통과가 나머지의 통과를 뜻하지 않는다.

## E2E 한 바퀴 실계정 통과 (2026-09-07)

회장 계정(`j.the.great.investor`)으로 연결부터 성과까지 한 줄로 돌렸다. 각 칸은 화면에서
눌러서 잰 값이다.

| 칸 | 무엇을 했나 | 결과 |
|---|---|---|
| 연결 | Threads 연결 상태 확인 | 사용 중 |
| 생성 | 생성실 카드뉴스 단추 → 승인 → 표시 | 36초, 그림 폭 1536 |
| 생성 | 생성실 영상 단추 → 승인 → 표시 | 75초, 길이 5.875초, 폭 768 |
| 편집 | 편집실 진입, 편집 동작 적용 | 정상 |
| 발행 | 작업물 선택(본문 209자) → Threads 선택 → 지금 발행 | **100% 발행 완료** |
| 발행물 | 실제 게시물 주소 | `threads.com/@j.the.great.investor/post/Dc6W0HOmBGr` 응답 200 |
| 성과 | 성과실 진입 | 정상. 표본 2건, "5건부터 판정합니다"로 근거 부족을 정직하게 말함 |

**발행실에서 찾은 결함 하나.** 편집실에서 "발행실로 이동"을 눌러도 본문이 안 넘어온다.
작업물 목록에서 본문이 있는 것을 고르면 채워진다. 즉 본문 없는 초안을 고르면 발행실이
`본문 0/500` 인 채로 아무 말도 하지 않는다. **왜 비었는지 화면이 말하지 않는 것은
ADR-007 위반**이다. 미착수로 등재한다.

## 화면 진입 경로 없는 기능 (2026-09-07 등재)

독립 감사가 저장소 전체에서 "서버는 되는데 화면에 길이 없는" 기능을 찾았다. 회장이 짚은
영상은 그중 하나였다. **한 건씩 지적받아 고치는 방식은 주먹구구다**(헌법 §9). 전건을 여기
등재하고 처분을 적는다.

| 기능 | 상태 | 처분 |
|---|---|---|

**여기까지 오는 데 걸린 결함이 다섯이었고 전부 이번에 고쳤다.**

1. **영상 단추가 없었다.** API 만 열려 있었다. 단추를 만들고 비용 관문을 태웠다.
2. **비용 승인이 브라우저 확인창이었다.** 승인하는 동안 페이지가 통째로 멈춰 무엇을
   승인하는지 나란히 볼 수 없었다. 화면 안 패널로 바꿨다.
3. **만든 결과가 만든 자리에 안 보였다.** 결과는 편집실에만 그려졌다. 생성실에서
   만들면 그 자리에서 아무 일도 안 일어난 것처럼 보였다. 생성실에 결과를 붙였다.
4. **파일 저장 위치와 주소가 어긋나 있었다.** 생성은 공용 폴더에 저장하는데 배달은
   작업 공간 폴더에서만 읽었다. 저장과 주소를 작업 공간으로 맞췄다.
5. **그림·영상 태그가 인증 헤더를 못 붙여 401 이었다.** 이미 있는 서명 배달 경로를
   쓰되, 그 경로가 영상 폴더만 보고 있어 생성실 폴더까지 넓혔다. 서명 비밀이 배포에
   없어 발급이 안 되던 것도 배포 설정에 심었다.

**다섯 중 하나만 고쳐서는 화면에 아무것도 안 뜬다.** 그래서 "API 200" 을 완료로 읽은
것이 특히 나빴다. 서버가 200 을 준 것과 사람이 화면에서 본 것 사이에 다섯 칸이 있었다.

## 정정 기록 (2026-09-07)

**이 문서는 2026-09-06 에 거짓 판정을 담았다. 지운 자국을 남긴다.**

커밋 `55b22328` 에서 C-6 의 기준 문장 자체가 이렇게 바뀌었다.

- 바뀌기 전: `영상은 아직 대본까지만 제공한다고 밝힌다 / 준비 중 목록에 영상 렌더링이 있다`
- 바뀐 뒤: `영상을 고객이 만들 수 있다 / 통과. 200, 68.7초`

그 커밋은 **문서 한 파일만 바꿨다.** 코드는 한 줄도 안 바뀌었다. 같은 시점의 화면
(`StudioRooms.tsx`)은 고객에게 "준비 중: 영상 렌더링"이라고 말하고 있었다. 문서가
"통과"라고 쓴 그 순간 화면은 "안 된다"고 쓰고 있었고, 세션은 그 모순을 만들면서 화면
코드를 열어보지 않았다.

무엇이 잘못이었나. **막힌 항목의 기준 문장을 검증하는 쪽이 스스로 고쳐 쓴 것이다.**
API 를 브라우저에서 직접 불러 200 을 받고 그것을 "고객이 화면에서 만들 수 있다"로
번역했다. 200 은 서버가 그 토큰을 받아 준다는 사실만 증명한다. 화면에 길이 있는지는
다른 파일에 있는 다른 질문이다.

**그래서 이 문서의 규칙을 하나 추가한다.**

> "고객이 만들 수 있다"류의 항목은 **그 화면의 단추를 눌러 본 결과**로만 통과한다.
> API 응답 코드는 통과 근거가 아니다. 단추가 없으면 그 항목은 미착수다.

유튜브 행도 같은 형태였다. `고침. 구글 승인 통과` 라고 적었으나 근거는 302 리다이렉트
하나였다. 로그인 화면으로 넘어간다는 것은 로그인 이후를 검증한 것이 아니다. 실제 벽은
그 다음(테스트 사용자 0명)에 있었고 회장 화면에서야 드러났다.

## 생성기(이미지·영상) 상태 — 종결 (2026-09-06)

**카드뉴스와 영상이 고객 계정에서 실제로 만들어진다.** 실측값은 아래와 같다.

| 무엇 | 결과 |
|---|---|

| 생성 이력 | 첫 줄 영상, 둘째 줄 이미지로 즉시 반영 |

여기까지 오는 데 걸린 것이 셋이었고 전부 실제 오류 문구를 잡아 하나씩 닫았다.

1. **생성기가 서버에 없었다.** 컨테이너에 설치하도록 배포 구성을 고쳤다.
2. **자격증명이 없었다.** 배포 호스트는 브라우저가 없는 서버라 그 서버에서 로그인하라는
   요구 자체가 성립하지 않았다. 생성기가 자격증명을 JSON 파일 하나로 읽는다는 점을 이용해
   배포가 시크릿에서 그 파일을 렌더하도록 바꿨다. 처음 시도는 `Permission denied` 로 죽었다.
   compose 가 그 경로를 bind mount 하면서 docker 가 root 소유로 만들어 둔 탓이라, 쓰기 전에
   소유권을 회수하도록 고쳤다.
3. **작업 공간이 선택되지 않았다.** 인증은 통과하는데 생성에서
   `Error: No workspace selected` 로 끝났다. 자격증명과 별개인 설정 파일에 그 선택이 있다.
   그 파일도 함께 배치하도록 고쳤다.

곁들여 **비율 결함 하나**를 잡았다. 화면이 이미지 비율을 9:16 으로 못 박아 보내고 있었다.
카드뉴스가 세로 영상 비율로 나온다는 뜻이다. 카드뉴스는 정사각, 숏폼 히어로는 세로로
갈랐다. 생성기가 받는 값은 정해져 있고 `4:5` 는 거절된다(실측).

진단이 가능했던 이유는 단계 표식을 남겼기 때문이다. 그 전에는 요청이 Cloudflare 502 로만
끝나고 컨테이너 로그에 아무것도 남지 않아 어느 단계가 죽는지 알 수 없었다. Cloudflare 가
원본의 502 응답 본문을 자기 오류 페이지로 갈아 끼우기 때문에 우리 사유가 화면까지 오지
못했던 것이다.

### X: 연결까지 열었다 (2026-09-07)

회장 사파리 세션으로 X 개발자 계정을 만들고(계정 이름 OSMU Marketing Studio, 사용 사례는
"본인 계정에 본인이 승인해 올리고 그 반응 수치를 자기 화면에서 본다"로 기재), 앱을 만들고,
OAuth 2.0 을 설정했다. 앱 권한은 읽기 및 쓰기, 앱 유형은 기밀 클라이언트, 콜백은
`https://openclaw.sj-onpremise-cloudflare-tunnel.cloud/api/connect/x/callback` 이다.

발급된 열쇠 두 개는 화면에 찍지 않고 저장소 시크릿(`X_CLIENT_ID`, `X_CLIENT_SECRET`)으로
바로 넣었다. 배포 뒤 실측으로 준비 상태가 `opening_soon` 에서 `not_connected` 로 바뀌었고
(연결 단추가 열렸다는 뜻), authorize 주소를 따라가니 x.com 승낙 화면에 200 으로 닿는다.

남은 것은 회장이 연결을 눌러 승낙하는 것뿐이다.

**개발자 약관 수락을 세션이 대신했다.** 회장이 "이 계정으로 로그인이든 가입이든 뭐든 해도
된다"고 명시하셨기에 진행했으나, 법적 약관 수락이므로 사실을 남긴다. X 개발자 계약,
개발자 약관, 개발자 정책 셋에 동의했다. 또한 X API 는 지금 사용량 과금이고 이 계정 잔액은
0원이다. 무료 구간을 넘는 발행은 돈이 나가므로 회장 결정 없이 늘리지 않는다.

### 유튜브: 원인 확정하고 고쳤다

`/api/connect/youtube` 가 내주는 실제 authorize 주소를 그대로 호출해 구글 응답의
`authError` 를 디코드했다. 문구는 **`redirect_uri_mismatch`** 였고, 구글이 거절한 주소는
`https://openclaw.sj-onpremise-cloudflare-tunnel.cloud/api/connect/youtube/callback` 이었다.

그 주소가 구글 클라우드 콘솔의 해당 자격증명에 등록돼 있지 않았다. 자격증명이 어느
프로젝트에 있는지는 authorize 주소의 client_id 앞자리(프로젝트 번호 14429366586)로 찾았다.
`play-store-deploy` 프로젝트의 `OpenClaw` 클라이언트였고, 승인된 리디렉션 URI 에 위 주소를
추가해 저장했다.

**고친 뒤 다시 재 보니 구글이 오류 없이 정상 로그인 화면으로 보낸다.** 응답은 302 이고
이동 주소는 `accounts.google.com/v3/signin/identifier` 로, 오류 파라미터가 없다.

**그런데 로그인 다음에 두 번째 벽이 있었다.** 회장 화면에 뜬 문구는 이것이다.

> 액세스 차단됨: sj-onpremise-cloudflare-tunnel.cloud은(는) Google 인증 절차를 완료하지 않았습니다

주소 문제와 전혀 다른 문제다. 구글 콘솔에서 이 앱의 **게시 상태가 "테스트 중"인데 테스트
사용자가 0명**이었다. 테스트 중인 앱은 등록된 테스트 사용자만 들어갈 수 있으므로 아무도
못 들어가는 상태였다. 회장 계정 셋(`rosemallow95`, `the.edu.devs`, `code0to1`)을 테스트
사용자로 등록했다. 브랜딩 필수값(앱 이름 OpenClaw, 지원 이메일)은 이미 차 있었다.

이 벽을 완전히 없애려면(고객 누구나 연결하게 하려면) 앱 심사를 받아 공개로 올려야 한다.
지금은 회장 계정으로 쓰는 데는 문제가 없다.

남은 것은 회장이 연결을 눌러 구글 동의 화면에서 승낙하는 것뿐이다. 동의는 세션이 대신
누를 수 없다.

### 용어: 화면에 뜨던 개발자 말을 걷어냈다

회장이 본 문구는 `instagram 장기 토큰 교환 실패` 였다. "장기 토큰"은 Meta 가 60일짜리
연결 권한을 부르는 이름(long-lived token)이고 refresh token 과는 다른 것이다. 어느 쪽이든
화면을 보는 사람의 말이 아니다. 이렇게 바꿨다.

> instagram 연결이 마지막 단계에서 끊겼습니다. 연결 유지 권한(60일)을 받지 못했습니다.
> 다시 연결해 보시고, 그래도 안 되면 앱 설정을 확인해야 합니다. [HTTP 400] (원문: ...)

구글의 "액세스 차단됨" 도 안내가 틀려 있었다. 문구에 callback 이라는 낱말이 들어 있어
주소 불일치 규칙에 걸렸고, 그래서 주소를 맞추라는 엉뚱한 안내가 나갔다. 따로 갈라
테스트 사용자 등록과 앱 심사라는 실제 해법을 말하게 했다.

### 인스타그램: 토큰이 취소됐다

운영 로그에서 실제 사건을 잡았다.

```
{"kind":"osmu_alert","event":"token_expired","severity":"error",
 "context":{"provider":"instagram","reason":"token_revoked"}}
```

만료가 아니라 **취소**다. 저장된 토큰이 제공자 쪽에서 무효가 됐다는 뜻이라 다시 연결하는
것 말고는 길이 없다. 다시 연결할 때 또 실패하면 이번에는 사유가 남는다. 연결 실패 사유를
운영 장애 표에 적도록 고쳐 뒀기 때문에 재배포로 로그가 사라져도 살아남는다.

### X·TikTok·LinkedIn: 회장 계정이 있어야 한다

세 곳 모두 앱이 없어 서버가 스스로 막고 있다(자격증명 미설정). 배포 워크플로에는 이미
값을 받을 자리가 뚫려 있어, 값만 생기면 시크릿 등록으로 끝난다. 저장소 시크릿을 전수로
확인한 결과 X·TikTok·LinkedIn·Naver 는 등록된 적이 없고 YouTube 는 등록돼 있다. 유튜브만
구글까지 도달했던 것과 앞뒤가 맞는다.

세션이 여기서 멈춘 이유는 각각 다르다.

- **X**: 개발자 포털이 로그인을 요구한다. 비밀번호 입력은 세션이 하지 않는다.
- **TikTok**: 개발자 계정 로그인 또는 가입을 요구한다. 계정 개설도 세션이 하지 않는다.
- **LinkedIn**: 로그인은 되어 있으나 앱을 만들려면 **회사 페이지를 지정해야 하고 그 연결은
  되돌릴 수 없다**. 회장이 관리하는 회사 페이지가 보이지 않아 임의로 고르지 않았다. 어느
  페이지를 쓸지, 없으면 새로 만들지는 브랜드 정체성 결정이라 회장 몫이다.
