# OSMU 편집실 v65 와이어프레임

## 설계 결론

편집실은 무엇을 만들지 고르고 결과물 자체를 고치는 곳이다. 어디에 올릴지는 발행실에서 정한다. 기존 v64의 4개 방 셸, 왼쪽 목차, 가운데 작업대, 오른쪽 담당 구조는 유지한다. 편집 형식은 글, 카드뉴스, 영상, 음악을 같은 수준으로 보여주고, 주 행동은 `발행실로 이동` 하나만 둔다.

### 기존 구현에서 유지한 기능

| 기존 기능 | 유지 방식 |
|---|---|
| 생성실, 편집실, 발행실, 성과실의 4개 방 | 같은 순서와 이름으로 유지 |
| 편집실 왼쪽 목차 | 글 문단, 카드 목록, 영상 장면, 대사 목록으로 형식에 맞춰 유지 |
| 결과물 가운데 작업대 | 글 전체 입력, 카드 캔버스, 영상 미리보기, 음악 안내로 확장 |
| 오른쪽 담당 | 전체 내용에 적용하는 일괄 수정만 둔다 |
| 자동 저장 | 저장 행동을 별도 단계로 만들지 않고 상태로 보여준다 |

## 1024 화면

```text
┌──────────────────────────────────────────────────────────────────────────────┐
│ OSMU  콘텐츠 공장 · 편집실                         고치는 대로 자동 저장됨 │
├────────────┬──────────────────────────────────────────────┬──────────────────┤
│ 작업 순서  │ 내용과 화면을 직접 다듬습니다               │ 전체에 한 번에   │
│ 생성실     │ 형식: [글] [카드뉴스] [영상] [음악]          │ 적용             │
│ 편집실     │ 형식과 채널은 다릅니다                       │ 전부 짧게 줄이기 │
│ 발행실     │                                              │ 높임말로 맞추기  │
│ 성과실     │ ┌──────────────┬───────────────────────────┐ │ 빈 줄 걷어내기  │
│            │ │ 글 문단      │ 글 전체 편집             │ │                  │
│            │ │ 1. 도입      │                           │ │ 마지막 저장     │
│            │ │ 2. 문제      │ [전체 글 자유 입력 영역] │ │ 07:10            │
│            │ │ 3. 해결 방법 │                           │ │                  │
│            │ │ 4. 마무리    │                           │ │ [발행실로 이동] │
│            │ └──────────────┴───────────────────────────┘ │                  │
└────────────┴──────────────────────────────────────────────┴──────────────────┘
```

- 주축: 셸은 행 64픽셀 뒤 3열 `176픽셀 | 가변 | 248픽셀`이다.
- 작업대 주축: 행 방향 `176픽셀 | 가변`이다. 820픽셀 미만에서 열 방향으로 바뀐다.
- 정렬선: 헤더, 본문, 오른쪽 담당의 좌우 여백은 모두 16 또는 24픽셀이다.
- 밀도: 작업 대상이 화면 세로의 절반 이상을 차지하고 설정은 결과물을 밀어내지 않는다.

## 390 화면

```text
┌──────────────────────────────┐
│ OSMU 편집실   자동 저장됨   │
├──────────────────────────────┤
│ 내용과 화면을 직접 다듬습니다│
│ [글] [카드뉴스] [영상] [음악]│
│ 형식과 채널은 다릅니다       │
│                              │
│ 글 문단                      │
│ [1. 도입] [2. 문제]          │
│                              │
│ 글 전체 편집                 │
│ [전체 글 자유 입력 영역]     │
│                              │
├──────────────────────────────┤
│ 마지막 저장 07:10            │
│ [발행실로 이동]              │
└──────────────────────────────┘
```

- 주축: 모든 작업 영역이 열 방향으로 흐른다.
- 오른쪽 담당은 168픽셀 높이의 하단 시트가 된다. 주 버튼은 하단 시트 안에서 항상 보인다.
- 글 입력 높이는 최소 320픽셀이다. 키보드가 열려도 본문이 독립 스크롤된다.

## 형식별 작업대

### 글

- 요소: 글 문단 목차, 글 전체 입력, 글자 수와 문단 수, 자동 저장 상태.
- 상호작용: 전체 글을 자유롭게 고친다. 문단을 나누거나 합쳐도 된다. 목차는 탐색용이며 입력을 자막 줄처럼 쪼개지 않는다.
- 긴 내용: 입력 영역 안에서 세로 스크롤한다. 긴 단어는 `overflow-wrap:anywhere`로 줄바꿈한다.

### 카드뉴스

- 요소: 카드 목록, 4:5 캔버스, 캔버스 안 텍스트 입력, 글자 위치 끌기 손잡이, 상단·중앙·하단 대체 선택, 비율·글자 크기·배경 이미지의 현재 값.
- 상호작용: 캔버스 안에서 글자를 직접 고친다. 끌기 위치는 상단·중앙·하단에 맞춰진다. 키보드나 터치에서는 위치 버튼을 쓴다.
- 명시 단위: `카드 비율 4:5 · 1080 × 1350픽셀`, `카드 글자 크기 기본 28픽셀`, `배경 이미지 책상 위 제품 사진`.

### 영상

- 요소: 장면 목차, 세로 영상 미리보기, 선택한 장면 대사, 영상 자막 글자 크기와 아래 여백.
- 상호작용: 장면을 고르고 그 장면의 대사를 고친다. 영상 편집이므로 이 형식에서만 장면 단위 입력을 쓴다.

### 음악

- 요소: 대사 목록, 나레이션 대사 입력, 미제공 기능 안내.
- 정직한 제한: `음악 파일 생성은 아직 제공하지 않습니다. 지금은 나레이션 대사만 편집할 수 있습니다.`
- 생성할 수 없는 음악 파일 옵션을 숨기거나 작동하는 것처럼 보이지 않는다.

## 상태 계약

| 상태 | 화면 | 다음 행동 | 막다른 길 방지 |
|---|---|---|---|
| 기본 | 선택한 형식의 실제 편집기 | 발행실로 이동 | 자동 저장 상태를 함께 표시 |
| 빈 상태 | 편집할 작업물이 없다는 원인 | 생성실에서 작업물 고르기 | 생성실로 돌아가는 길 제공 |
| 불러오는 중 | 이전 값 대신 뼈대 화면 | 없음 | 발행실 이동 비활성, 중복 수정 방지 |
| 오류 | 원인, 마지막 저장본 보존 여부 | 다시 불러오기 | 데이터가 사라졌다고 오해하지 않게 함 |
| 긴 내용 | 목차 12개, 긴 본문 | 발행실로 이동 | 가로 넘침 없이 목차와 본문 독립 스크롤 |
| 미제공 | 음악 파일 생성 범위 | 나레이션 대사 편집 | 제공 범위를 문장으로 공개 |

## 상호작용과 심리 근거

| 결정 | 근거 | 적용 |
|---|---|---|
| 형식과 플랫폼 분리 | 힉의 법칙. 서로 다른 결정을 한 줄에 놓으면 선택 비용이 늘어난다 | 편집실에는 형식만, 발행실에는 채널만 둔다 |
| 결과물 직접 편집 | 야콥의 법칙. 사용자는 Canva와 문서 편집기에서 보던 직접 조작을 기대한다 | 글은 전체 문서 입력, 카드는 캔버스 안 입력과 위치 이동 |
| 주 버튼 하나 | 포그 행동모델. 동기와 능력이 있어도 촉발이 모호하면 행동하지 않는다 | 저장은 자동 상태, 주 행동은 발행실로 이동 하나 |
| 오류에 보존 여부 표시 | 닐슨 오류 회복 원칙 | 마지막 저장본이 남았는지와 재시도 행동을 함께 말한다 |

## 벤치마크 적용

- [Canva 텍스트 편집](https://www.canva.com/help/add-and-edit-text/): 캔버스 안 텍스트를 선택한 자리에서 바로 고치는 방식을 차용했다. OSMU는 자유 배치 복잡도를 줄이고 상단·중앙·하단 맞춤을 함께 제공한다.
- [Canva 위치와 정렬](https://www.canva.com/help/layer-group-align/?query=group): 요소 끌기와 정렬 도구를 참고했다. OSMU는 첫 사용자의 실수를 줄이기 위해 세 구역에 맞춰진다.
- [Google Docs 문서 편집](https://support.google.com/docs/answer/7068618?hl=ko): 한 문서를 연속된 본문으로 고치는 관습을 차용했다. 자막 줄처럼 문단마다 입력을 강제하지 않는다.
- 차별화: 채널별 캡션과 게시 조건은 편집기에서 제외하고 발행실 한 곳에서만 다룬다.

## 레드팀과 수정

까다로운 고객의 공격: 자동 저장만 보이면 저장 시점을 믿지 못하고, 카드 위치 끌기는 정교하지 않다고 느낄 수 있다.

수정: 마지막 저장 시각을 주 버튼 바로 위에 표시했다. 카드 끌기는 정밀 좌표가 아니라 상단·중앙·하단에 맞춰지고 같은 동작을 위치 버튼으로도 수행하게 했다. 정밀 자유 배치는 현재 범위로 약속하지 않는다.

## 셀프심문

질문: 내가 바꾼 화면을 회장이 처음 보면 무엇을 눌러야 할지 3초 안에 아는가?

답: 편집 중에는 결과물 자체가 가장 크고, 다음 단계는 화면 오른쪽 또는 모바일 하단의 파란 `발행실로 이동` 하나다. 저장 버튼을 없애고 자동 저장 상태를 버튼 바로 위에 두어 다음 행동과 저장 여부를 동시에 읽게 했다. 다만 형식 선택과 발행실 이동을 모두 같은 강조색으로 쓰면 시선이 갈릴 수 있어, 형식은 테두리 선택으로 낮추고 주 버튼만 채운 강조색으로 유지했다.

이 결론이 틀렸다면 가장 그럴듯한 이유: 사용자가 발행 채널을 편집 중에도 미리 확인하고 싶을 수 있다. 그러나 회장 지적 R-S10-34의 핵심은 두 결정이 섞인 것이므로 편집실에 플랫폼 선택을 다시 넣지 않는다. 대신 `올릴 채널과 채널별 문구는 발행실에서 정합니다`라는 경계 안내를 한 번만 둔다.
