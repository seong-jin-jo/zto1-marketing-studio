# OSMU 발행실 플랫폼 필드 v66 와이어프레임

## 설계 결론

기존 v64의 4개 방 셸, 일곱 플랫폼 미리보기, 미리보기 안 직접 편집, 발행 선택, 임시 저장, 검토 요청, 지금 발행, 예약 발행을 유지한다. 이번 변경은 계정 표시 이름과 사용자명을 편집 대상에서 빼고, 플랫폼마다 실제로 존재하는 게시 필드와 제한만 남긴다.

### 기존 구현에서 유지한 기능

| 기존 기능 | 유지 방식 |
|---|---|
| Threads, X, Instagram, Facebook, YouTube Shorts, Instagram Reels, TikTok 일곱 미리보기 | 기본 상태에서 두 열 격자로 모두 보여 준다. 플랫폼 필터는 집중 보기일 뿐 삭제가 아니다 |
| 미리보기 안 직접 편집 | 제목, 본문 또는 캡션, 해시태그 또는 주제 태그, 발행 뒤 첫 댓글을 카드 안에서 고친다 |
| 플랫폼별 발행 선택 | 카드 머리 체크 상자를 유지한다 |
| 발행 뒤 첫 댓글 | 현재 지원 4곳에만 입력을 유지하고 나머지 3곳은 미지원 이유를 보여 준다 |
| 자동 저장 | 헤더에 상태를 유지한다 |
| 임시 저장, 검토 요청, 지금 발행, 예약 발행 | 오른쪽 발행 행동 열과 모바일 하단 행동 영역에 유지한다 |

### 추가 또는 변경한 것

| 변경 | 새 계약 |
|---|---|
| 표시 이름 입력 | 삭제. 아바타, 표시 이름, 사용자명을 읽기 전용 계정 머리로 표시 |
| 표시 이름 일괄 통일 | 삭제. 계정 정체성은 게시물 일괄 편집 대상이 아님 |
| 잘못 연결한 계정 수정 | `연결 계정 바꾸기`로 해결. 게시물 값을 고치는 입력과 분리 |
| 공통 캡션 한도 | 플랫폼별 공식 계산으로 교체. X는 가중 문자, YouTube 설명은 바이트, Instagram은 캡션과 해시태그 합계 |
| 공통 해시태그 입력 | Threads는 주제 태그 1개. X는 2개 권고. Facebook과 TikTok은 공식 고정 개수 미확인 상태 |
| 내부 용어 | `승인 인박스`는 `검토 대기`, 행동은 `검토 요청하기`. `운영자 API`는 제품 UI에서 사용하지 않음 |

## 1024 화면

```text
┌──────────────────────────────────────────────────────────────────────────────┐
│ OSMU  콘텐츠 공장 · 발행실                         고치는 대로 자동 저장됨 │
├──────────┬───────────────────────────────────────────────┬───────────────────┤
│ 작업 순서│ 올라갈 모습을 채널마다 확인합니다            │ 발행 준비         │
│ 생성실   │ 계정 정보는 읽기 전용입니다                  │ 7곳 선택됨        │
│ 편집실   │ [전체 7곳] [Threads] [X] [Instagram] ...      │ 확인할 규격 2개   │
│ 발행실   │                                               │                   │
│ 성과실   │ ┌──────────────────┐ ┌──────────────────┐    │ [임시 저장하기]  │
│          │ │ Threads       □ │ │ X             □ │    │ [검토 요청하기]  │
│          │ │ [계정 정보 읽기]│ │ [계정 정보 읽기]│    │ [지금 발행]      │
│          │ │ 본문       0/500│ │ 본문       0/280│    │ [예약 발행]      │
│          │ │ [직접 편집]      │ │ [직접 편집]      │    │                   │
│          │ │ 주제 태그   1/1 │ │ 해시태그 2개 권고│    │                   │
│          │ └──────────────────┘ └──────────────────┘    │                   │
│          │ ┌──────────────────┐ ┌──────────────────┐    │                   │
│          │ │ Instagram       │ │ Facebook         │    │                   │
│          │ │ 캡션+태그 0/2200│ │ 본문 규격 확인 필요│  │                   │
│          │ └──────────────────┘ └──────────────────┘    │                   │
└──────────┴───────────────────────────────────────────────┴───────────────────┘
```

- 셸 주축: 행 64픽셀 뒤 3열 `160픽셀 | 가변 | 248픽셀`이다.
- 미리보기 주축: 2열 행 방향이다. 카드 내부는 계정 머리, 게시 필드, 미디어 규격의 열 방향이다.
- 카드 순서: 플랫폼 이름과 선택, 읽기 전용 계정, 게시물 편집, 미디어 규격이다.
- 정렬선: 셸과 카드 여백은 8, 16, 24, 32픽셀만 사용한다.
- 밀도: 계정 정보는 64픽셀 머리에 모으고, 실제 편집 필드가 카드 면적의 절반 이상을 차지한다.

- 주축: 모든 미리보기가 한 열로 흐른다.

- 플랫폼 필터는 줄바꿈하며 가로 스크롤하지 않는다.
- 카드의 표시 이름과 사용자명은 각각 한 줄 말줄임이다. 원문은 `title`로 확인할 수 있다.

## 계정 머리 상태

| 상태 | 표시 | 행동 | 막다른 길 방지 |
|---|---|---|---|
| 연결됨 | 아바타, 표시 이름, 사용자명, 읽기 전용 안내 | 연결 계정 바꾸기 | 게시물 편집과 계정 교체를 분리 |
| 미연결 | `연결된 계정이 없습니다` | 계정 연결하기 | OAuth 연결로 이동 |
| 불러오는 중 | 계정 머리 뼈대 화면 | 없음 | 편집 입력 비활성 |
| 오류 | `계정 정보를 불러오지 못했어요` | 연결 상태 다시 확인하기 | 고친 게시물 보존 여부 함께 표시 |
| 심사 전 | `플랫폼 연결 준비 중` | 제공되는 테스트 절차 보기 | ADR-006에 따라 App Review 통과 뒤 자동 제거 |

| 긴 내용 | 10문장 본문과 34개 해시태그 | 초과 필드 수정 | 규격 통과 뒤 발행 |
| 공식 상한 미확인 | `규격 확인 필요` | 업로드 전 검사 결과 확인 | 통과 또는 플랫폼 오류와 복구 행동 |
| 하드 제한 초과 | 붉은 카운터와 해당 필드 | 초과분 수정 | 제한 이내 |
| 권고 초과 | 주황 경고 | 그대로 발행 또는 수정 | 발행 가능 |

## 상호작용과 심리 근거

| 결정 | 근거 | 적용 |
|---|---|---|
| 계정 정보와 게시물 필드 분리 | 개념 모형 일치. 사용자는 프로필과 게시물을 다른 객체로 이해한다 | 계정 머리는 읽기 전용 지면, 본문은 입력 지면 |
| 플랫폼별 필드만 표시 | 야콥의 법칙. 사용자는 각 플랫폼에서 보던 이름과 규칙을 기대한다 | Threads 주제 태그, Shorts 제목과 설명, TikTok 공개 범위 |
| 하드 제한과 권고 구분 | 오류 예방과 사용자 통제 | 하드는 붉은 차단, 권고는 주황 안내와 발행 가능 |
| 미확인 숫자를 숨기지 않음 | 신뢰 형성. 거짓 정밀도 방지 | `규격 확인 필요`와 다음 검증 행동을 한 자리에서 표시 |

## 벤치마크 적용

- [Threads 공식 게시 규격](https://developers.facebook.com/docs/threads/posts): 일반 해시태그 묶음을 별도 주제 태그 하나로 바꿨다.
- [X 공식 문자 계산](https://docs.x.com/fundamentals/counting-characters): 단순 문자열 길이 대신 X 가중 카운터 계약을 정의했다.
- [Instagram 미디어 생성](https://developers.facebook.com/docs/instagram-api/reference/ig-user/media): 캡션과 해시태그가 공유하는 2,200자와 30개 제한을 함께 보이게 했다.
- [TikTok 콘텐츠 공유 지침](https://developers.tiktok.com/docs/en/content-sharing-guidelines): 계정 닉네임과 사용자명을 표시하고 공개 범위와 상호작용을 사용자가 직접 확인하게 했다.
- 차별화: 플랫폼의 게시 화면을 흉내 내는 데 그치지 않고 연결 계정 소유권, 공식 상한의 근거 수준, OSMU 첫 댓글 지원 여부를 한 카드에 합쳤다.

## 레드팀과 수정

까다로운 고객의 공격: 일곱 카드가 길어져 중요한 문제를 찾기 어렵고, 읽기 전용 계정 이름을 잘못 연결했을 때 고칠 방법이 없어 보인다.

수정: 기본은 일곱 카드를 보존하되 상단 필터로 문제가 있는 플랫폼 하나에 집중할 수 있게 했다. 계정 머리에 `연결 계정 바꾸기`를 두고 표시 이름 입력은 만들지 않았다. 오른쪽 발행 준비에는 선택한 곳과 확인할 규격 수만 요약한다.

## 셀프심문

질문: 이 설계가 틀렸다면 가장 그럴듯한 이유는 무엇인가?

답: 플랫폼 규격이 바뀌는데 화면에 고정 숫자가 남는 것이다. 그래서 규격 문서를 기준일과 출처가 있는 참조 파일로 분리하고, 계정별 값인 TikTok 동영상 길이는 게시 직전 응답을 읽게 했다. 공식 고정 수치를 확인하지 못한 값에는 숫자를 만들지 않았다.

질문: 내가 적은 규격 중 출처 없이 기억으로 쓴 값이 있는가?

답: 없다. 수치는 `docs/reference/플랫폼-발행-필드-규격-2026-09-01.md`의 공식 출처에서 가져왔다. Facebook 본문과 해시태그, TikTok 해시태그 개수는 공식 수치를 확인하지 못해 `규격 확인 필요`로 남겼다.
