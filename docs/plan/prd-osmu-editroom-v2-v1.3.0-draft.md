# OSMU 편집실 v2 PRD v1.3.0 (초안, 템플릿 고르기 · 영상 표지 · 인트로·아웃트로 고르기 · 글 후보 개정판)

생성실이 뽑은 초안을 편집실에서 **손으로 바로 고쳐** 완성하고, 같은 작업물을 채널별 규격으로 내보내 발행실에 넘긴다. 카드뉴스는 Canva·미리캔버스처럼 슬라이드 위에서 요소를 끌어 고치고, 영상은 CapCut·Vrew처럼 재생하며 고친 것이 **실제로 나가는 영상 파일에 그대로 들어간다.** v1.3.0 부터는 **카드뉴스 모양(템플릿)을 고르고 갈아탈 수 있고, 영상 표지와 인트로·아웃트로를 보고 골라 넣으며, 글은 각도가 다른 후보 3개 중 하나를 골라 이어서 고친다.**

> **회장 확정 지시 기반 초안.** 범위는 회장이 2026-10-01 두 번 지시했다(R-26). 2026-10-02 R-27 보강 지시("템플릿 선택하는 Ux도 설계가된건가? … 그리고 진행해")를 v1.3.0 에 반영했다. 이 문서는 그 범위를 다시 묻지 않는다. 화면 배치와 흐름은 추천안으로 확정해 적었다. 회장 판단이 필요한 것은 **여전히 하나뿐**이다: 영상 모션그래픽 구간에 Remotion 을 들이는 것의 확인(§13 결정 1). R-27 은 회장 결정 항목을 새로 만들지 않는다(돈·비가역·정체성에 해당하는 것이 없다, §13 서두). 실발행 시험 계정은 회장 답으로 해소됐다(§13 결정 2). 승인 절차는 plan-critic 비평 후 `/approve plan` 이다.

## 0-2. v1.3.0 변경 요약 (회장 R-27: 템플릿 고르기 · 영상 표지 · 인트로·아웃트로 고르기 · 글 후보)

**왜 고쳤나.** 회장 R-27 원문: "카드뉴스는 무조건 카톡대화처럼 간다는건 아니다 알지? 하나의 템플릿이고 그렇게 되어있는거같은데 혹시나싶어서. 템플릿 선택하는 Ux도 설계가된건가? 영상쪽은 썸네일이나 인아웃트로같은거도 선택해서 삽입하던가...알지? 글 같은경우는 편집실에서는 따로 편집할수도 있고 아니면 여러버젼 보여주면서 선택하는건 어떨까 그냥제안. 그리고 진행해". v1.2.0 과 운영 코드를 대조한 결과는 넷이다.

1. **카톡 대화는 용어상 템플릿 2계열 중 하나였지만(§4 "장 템플릿"), 고르고 갈아타는 화면 요구가 없었다.** 운영 생성실의 카드뉴스 주 단추는 "카톡 말풍선 카드뉴스 9장 만들기" 이고, 운영 템플릿 등록부에는 `chat_bubble` 하나만 그려진다(`main:dashboard/src/lib/studio/card-templates/index.ts`). 회장이 의심한 "카톡이 기본처럼 굳어 있다" 는 사실이다. v1.2.0 에는 C-12 "템플릿에서 장 추가" 와 C-15 "내 템플릿 저장" 만 있었다.
2. **영상 표지(썸네일)는 PRD 에 0건이었다.** 운영에는 발행실 카드 머리줄에 "대문 시점(초)" 입력이 이미 있다(TikTok·Reels만, YouTube 는 "자동으로 고릅니다" 고지, `main:dashboard/src/lib/video-cover.ts`·`PublishHeaderControls.tsx`). 프레임을 눈으로 고르기, 사진 올리기, 표지 글 얹기는 없다.
3. **인트로·아웃트로는 V-04 에 "넣기" 는 있었지만 "보고 고르는 화면" 이 요구 수준으로 없었다.** 미리 재생, 바꾸기, 빼기, 길이 조절의 수용 기준이 없었다.
4. **글은 편집실 글 편집기(본문 하나 + 채널별 글자 수 상한 미터)로 고칠 수 있다.** 생성은 채널마다 1개씩만 나온다(`main:dashboard/src/app/api/studio/text/route.ts` 출력 JSON 이 채널당 한 칸). 생성실의 구조 초안 A/B/C 는 "무엇을 말할지(이야기 순서)" 의 후보이지 채널별 완성 글의 후보가 아니다. 회장 제안 "여러 버전 보여주고 고르기" 는 채택했다.

## 0-1. v1.2.0 변경 요약 (영상 렌더 도구: 양자택일을 역할 분담으로)

**왜 고쳤나.** v1.1.0 §13 결정 1은 "ffmpeg + ASS 대 Remotion" 중 하나를 고르라고 물었다. 회장 지적(2026-10-02, "둘이 경쟁이야? remotion은 모션그래픽만드는게 아니었나?")대로 이것은 잘못 세운 양자택일이었다. 세 도구는 하는 일이 다르다.

- **ffmpeg**: 영상·음성 파일을 변환하고 자르고 이어붙이고 합성하는 명령줄 도구. 지금 운영 서버에서 자막 굽기와 나레이션 합성에 쓰고 있다.
- **ASS**: 글자 모양(글꼴·색·위치)과 글자 애니메이션을 담는 자막 파일 형식. 도구가 아니라 파일 형식이다.
- **Remotion**: React 코드로 영상을 만드는 프레임워크. 인트로·아웃트로·움직이는 제목 같은 모션그래픽을 만드는 데 쓰고, 4.0부터 ffmpeg 를 내장해 영상 파일로 내보낸다([remotion.dev/docs/ffmpeg](https://www.remotion.dev/docs/ffmpeg)).

ASS 는 자막 파일이라 인트로·아웃트로·모션그래픽 요구(R-26-4, E-5·E-6)를 혼자 감당하지 못한다. Remotion 은 그 빈자리를 채우는 도구이고 ffmpeg 를 대체하지 않는다. 그래서 둘 중 하나를 고르는 문제가 아니라 **누가 무엇을 맡느냐**의 문제다.

## 1. 한 줄 결론

편집실 v70은 "카톡 말풍선을 그 자리에서 고친다"와 "대본 줄을 지우면 컷이 표시된다"까지 왔다. 그러나 **사진·글 카드는 위치 세 칸(상·중·하)만 고를 수 있고, 영상은 컷·오버레이를 화면에만 표시할 뿐 나가는 영상에는 반영하지 않으며, 인트로·아웃트로·모션그래픽은 0개, 채널별 비율 내보내기도 없다.** 이 증분은 그 네 구멍을 닫는다.

One Thing(이 증분): **1인 브랜드 대표가, 생성된 초안을 프롬프트를 다시 쓰지 않고, 화면에 보이는 그대로 손으로 고쳐서 채널마다 맞는 크기로 내보내는 곳.**

### 2.3 v70이 자유 배치를 기각한 이유와, 이번에 여는 이유

v70 카드 와이어프레임(§9)은 "말풍선 템플릿은 세로 흐름 + 좌우 정렬이 규격이라 자유 좌표가 필요 없다"며 자유 배치를 2단계로 미뤘고, Fabric·Konva 같은 캔버스 라이브러리 전면 도입은 기각했다. 그 판단은 **말풍선 장에 대해서는 여전히 맞다.** 이번 증분은 그 결정을 뒤집지 않고, v70이 미리 넣어 둔 "요소마다 자유 배치 칸(frame)" 모델을 **사진·글 카드와 모든 장의 덧붙임 요소(로고·스티커·글 상자)** 에 실제로 연다. 말풍선 묶음은 계속 세로 흐름이다. 회장 R-26이 "배경 위에 글자를 아무 데나" 를 요구했으므로 v70 레드팀 메모가 예고한 확장 시점이 지금이다.

## 3. 이번 증분이 정하는 것과 정하지 않는 것

**정한다**
- 카드 편집기의 요소 종류, 조작(선택·이동·크기·회전·레이어·글꼴·색·이미지 교체), 장 조작
- 카톡 대화형의 대화 튜닝 기능 3종
- 영상 편집기의 실반영 범위(컷·인트로·아웃트로·글자 애니메이션·스티커·전환·자막 스타일·배경음악·오버레이)
- 채널별 내보내기 규격과 비율 전환 규칙, 발행실 인계 조건
- 직접 조작과 AI 보조의 역할 분담
- 단계별 출하 순서와 1차 범위
- 수용 기준과 품질 판정 지표
- 영상 렌더 도구의 **역할 분담**(추천안, §8.3): ffmpeg 가 조립·자막·합성, Remotion 이 모션그래픽 짧은 구간. Remotion 도입 자체는 회장 확인(§13 결정 1)
- (v1.3.0) 카드 템플릿 고르기·바꾸기의 흐름과 글 보존 규칙, 1단계 템플릿 6종의 이름과 용도(§7.7)
- (v1.3.0) 영상 표지 고르기와 채널별 전달 규칙(§7.8), 인트로·아웃트로 고르는 서랍(§7.4 V-16·V-17)
- (v1.3.0) 글 후보 3개의 각도·추천·편집기 연결·사실 경고(§7.9)
- (v1.3.0) 생성실 쪽은 **템플릿 줄 하나(TP-01)와 글 후보 생성(W-01·W-02)** 만 정한다. 생성실 흐름(조건 질문 → 구조 초안 A/B/C → 결과물 만들기)과 비용 확인은 v2.1.0 그대로

**정하지 않는다(하류)**
- 템플릿 6종의 시각 디자인(글꼴 조합·색·장식) → 디자인(v72). 이 문서는 이름·용도·구성 장 수·글 보존 규칙까지
- 글 후보를 한 번의 생성 요청으로 받을지 나눠 받을지, 저장 필드 → 기술설계. 이 문서는 "비용 확인 1회, 대기 화면 1회" 라는 사용자 쪽 조건만 건다(W-01)
- 화면 픽셀·여백 → 디자인(v71 시안). 단 §6의 배치 원칙은 추천안으로 확정
- 렌더 파이프라인의 구체 구성(카드 PNG 를 브라우저에서 그릴지 서버 헤드리스 브라우저로 찍을지, 렌더 작업자 배치, 모션 구간 중간 파일 형식, 저장 필드, API 모양) → 기술설계(회장 티키타카, 헌법 §4.4). 영상 도구의 역할 분담 원칙은 위 "정한다" 에서 추천안으로 정했고, 기술설계는 그 원칙 안에서 구성을 고른다
- 가격 숫자 → 기존 과금 결정(D-014)을 따른다. AI 보조 호출은 생성과 같은 비용 승인 관문을 탄다

## 5. 직접 조작과 AI 보조의 역할 분담 (D-2026-09-09-1 적용)

결정 원장은 처음에 "직접 편집이 기본, AI는 보조"로 썼다가 회장 정정으로 **"서열이 아니라 역할 분담, 기준은 변경의 크기와 종류"** 로 고쳤다. 위임 문구는 앞의 표현을 썼지만 이 문서는 정정된 결정을 따른다. 편집실의 모든 조작은 손으로 끝낼 수 있어야 하고, AI는 손으로 하면 여러 번 반복해야 하는 일만 맡는다.

| 변경 | 수단 | 예 |
|---|---|---|
| 한 곳을 정확히 | **직접 조작만.** AI 경로를 기본으로 띄우지 않는다 | 글자 하나 고치기, 요소 끌기, 색 바꾸기, 컷 하나 |
| 같은 규칙을 여러 곳에 | **AI 보조 또는 일괄 조작** | 말투 다듬기(선택한 말풍선 또는 덱 전체), 자막 전체 어투 바꾸기, 무음·군말 일괄 컷 |
| AI 결과 반영 | 반드시 **전후 비교 후 사람이 적용**. 적용 뒤 되돌리기 1회로 원상 복구 | 말투 다듬기 결과 3개 후보 중 고르기 |

AI 보조 호출은 비용이 들 수 있으므로 실행 전에 금액을 보여 준다(D-014). 금액이 0원이면 "무료"라고 적는다.

## 6. 화면 원칙 (추천안 확정, 디자인 v71이 픽셀로 옮긴다)

v70 셸(헤더 2층, 좌 사이드바, 오른쪽 담당 대화창 304px, 형식 탭 3개, 저장 상태)은 그대로 둔다. 바뀌는 곳은 가운데 작업 영역뿐이다.

- **카드뉴스**: 왼쪽 장 스트립(v70 112px 계승) · 가운데 캔버스 · 캔버스 위 **선택 요소를 따라다니는 떠 있는 도구막대**(v70 말풍선 툴바와 같은 방식). 요소 추가(글·이미지·도형·스티커·로고)는 캔버스 위쪽 한 줄 도구줄. 세부 속성(글꼴·크기·색·투명도·정렬)은 도구막대에서 펼친다. 오른쪽에 속성 패널을 새로 만들지 않는다. 오른쪽 304px은 이미 담당 대화창이 쓰고 있고, 폭을 더 빼면 캔버스가 520px 아래로 줄어 v70 실측 결함(카드 115px 눌림)이 재발한다.
- **영상**: v70 배치 계승. 위 줄 = 9:16 플레이어(288px) + 대본, 아래 = 타임라인. 타임라인 레인을 3개에서 **5개**로 늘린다: 영상(인트로·본편·아웃트로 블록) · 자막 · 글·스티커 · 훅·CTA·댓글 · 배경음악. 인트로·아웃트로·스티커·애니메이션 고르기는 타임라인 위 도구줄의 "넣기" 단추가 여는 서랍(모음 목록)에서.
- **비율판 전환**: 형식 탭 줄 오른쪽(저장 상태 왼쪽)에 비율 칩. 카드 4:5 · 1:1 · 9:16, 영상 9:16 · 1:1 · 16:9. 칩을 누르면 같은 작업물의 그 비율판으로 바뀐다.
- **(v1.3.0) 템플릿 바꾸기**: 카드뉴스일 때 형식 탭 오른쪽에 "템플릿: 카톡 대화 ▾" 처럼 **지금 템플릿 이름이 적힌 단추** 1개(v71 머리줄의 "템플릿 전환" 자리). 누르면 캔버스 위로 갤러리 서랍이 내려온다. 오른쪽 304px 담당 대화창은 건드리지 않는다.
- **(v1.3.0) 영상 표지**: 영상 넣기 서랍의 탭에 "표지" 를 더한다(인트로·아웃트로 탭 왼쪽 첫 탭). 고른 표지는 타임라인 영상 레인 맨 앞에 작은 정지 그림 칩으로 보인다(재생 길이에는 들어가지 않는다).
- **(v1.3.0) 글 후보**: 글 형식 편집실의 채널 탭 아래, 글 편집기 바로 위에 **후보 칩 줄**(질문형 · 숫자형 · 고통 인식형, 추천에 "추천" 배지). 칩을 누르면 편집기 옆에 비교 보기가 열리고, "이 후보로" 를 눌러야 본문이 바뀐다. 후보 칩 줄은 접을 수 있고 접힌 상태가 기억된다.
- **390px(모바일)**: 카드는 장 스트립이 가로로 내려가고 도구막대는 캔버스 아래 고정 줄(44px 터치)로 바뀐다(v70 §3.3 규칙 계승). 회전·레이어 조작은 모바일에서도 된다. 영상은 플레이어 위·대본 아래 세로 배치(v70 §4.1).

## 7. 요구와 수용 기준

모든 요구는 Given/When/Then 수용 기준을 하나 이상 갖는다. **단계** 열이 출하 순서다(§9). "현재" 열의 출처는 §2.2.

### 7.1 카드뉴스: 사진·글 템플릿 (E-2)

| ID | 요구 | 묶음 | 현재 | 수용 기준 |
|---|---|---|---|---|

### 7.7 카드뉴스 템플릿 고르기와 바꾸기 (v1.3.0, R-27-2 · R-27-3)

## 8. 품질 판정 기준과 기술 리스크

### 8.1 미리보기 일치 판정 (자동 테스트, CI)

**1차 판정은 글자 배치다. 픽셀 비교는 보조다.** 한글 카드가 깨지는 방식은 거의 언제나 "줄바꿈 위치가 한 글자 어긋남"이고, 픽셀 1%는 그것을 놓친다(긴 문장 한 글자가 다음 줄로 넘어가도 전체 픽셀 차이는 1% 미만일 수 있다).

| 대상 | 1차 기준(하나라도 어기면 실패) | 보조 기준(경고, 추세 관찰) |
|---|---|---|
| 카드 PNG | 글 요소마다 경계 상자 위치·크기 차이 ≤ 2px(1080 기준) · **줄바꿈 위치 100% 동일 · 줄 수 동일** | 장 전체 다른 픽셀 비율 ≤ 1%(색 차이 임계 적용) |
| 영상 | **같은 시각 정지 캡처** 비교. 지정 시각 10개(인트로 끝·컷 경계·애니메이션 시작/끝·아웃트로 시작 포함)에서 글 요소 경계 상자 ≤ 4px, 자막 줄바꿈 위치·줄 수 동일 | 다른 픽셀 비율 ≤ 3% (unsourced: 첫 실험선) |
| 영상 시간 | 컷 반영 뒤 길이 오차 ≤ 0.1초, 자막·음성 어긋남 ≤ 0.1초 | |

**비교 대상과 환경**
- 편집 화면 쪽은 **Chromium과 WebKit(사파리 엔진) 두 브라우저**에서 각각 렌더해, 둘 다 서버 내보내기 결과와 비교한다. 회장과 고객 일부가 사파리를 쓴다(메모리 기록: 회원 Safari 세션). 한 브라우저만 맞추면 다른 쪽 고객이 깨진 미리보기를 본다.
- 내보내기 쪽은 **고정된 서버 환경**(같은 컨테이너 이미지, 같은 글꼴 파일)에서 만든다. 개발자 맥에서 만든 PNG를 기준으로 삼지 않는다.
- **픽스처 필수 항목**: 글꼴 9종, 회전, 레이어 겹침, 한글 긴 문장, 일부 글자 색, **카톡 장의 편집 전용 여백 34px이 내보내기에 섞이지 않는지**(v71 §10-5. 고른 말풍선 아래 툴바 자리는 편집 화면에만 있다). 이 마지막 픽스처는 말풍선을 고른 상태로 내보내기를 눌러 확인한다.
- **(v1.3.0) 추가 픽스처**: ①템플릿 6종 각각의 표지·본문 장(TP-01 썸네일과 내보낸 PNG 가 같은 렌더 경로인지) ②카톡 대화 9장 → 큰 제목 표지형 → 다시 카톡 대화로 왕복한 덱(글자 수·숫자·고유명사 보존, TP-02·TP-03) ③영상 표지 이미지(표지 글 프리셋 2종, VC-02)

### 8.3 영상 렌더 도구 역할 분담 (추천안, Remotion 도입은 회장 확인)

세 도구는 경쟁 관계가 아니다. 각자 다른 일을 하고, 한 편의 mp4 는 셋이 나눠 맡아 만든다. CapCut 이 인트로 템플릿을 끌어 넣으면 본편 앞에 붙는 것과 같은 구조를 서버에서 재현한다.

```
편집 결정 목록(컷·인트로·아웃트로·자막·오버레이·전환·음악, §4)
   │
   ├─ 모션 구간 ──▶ Remotion 렌더 (수 초짜리 인트로·아웃트로·움직이는 제목 클립)
   │                 같은 입력이면 재사용(V-05 "항상 넣기")
   │
   ├─ 글자 층 ────▶ ASS 자막 파일 1개 (자막·훅·CTA·댓글·글자 애니메이션 4종)
   │
   └─ 본편 ───────▶ 원본 영상 + 나레이션(목소리 변경 시 새로 합성)
                         │
                         ▼
               ffmpeg 조립: 컷 적용 → 모션 구간 이어붙이기 → 전환 → ASS 굽기 → 음악 섞기
                         │
                         ▼
                  비율판별 mp4 (9:16, 2단계 1:1·16:9)
```

| 도구 | 한 줄 정의 | 이 증분에서 맡는 일 | 운영 상태 | 비용 |
|---|---|---|---|---|
| ffmpeg | 영상·음성 변환·합성 명령줄 도구 | 컷 적용, 인트로·본편·아웃트로 이어붙이기, 전환, ASS 자막 굽기, 나레이션·배경음악 합성, 비율판 출력 | **운영 중**(자막 굽기·나레이션 합성) | 0원(오픈소스) |
| ASS | 글자 스타일·애니메이션을 담는 자막 파일 형식 | 영상 위 모든 글자 층의 정의. 미리보기(JASSUB)와 굽기(ffmpeg libass)가 같은 파일을 읽는다(T-4) | 운영 자막 굽기는 지금 drawtext 방식, ASS 전환은 묶음3 | 0원 |
| Remotion | React 코드로 영상을 만드는 프레임워크 | V-04 인트로·아웃트로 템플릿(브랜드 키트 로고·색·글꼴을 코드 값으로 받음), 움직이는 제목 카드, 2단계 카운트업·형광펜 밑줄. 결과 클립을 ffmpeg 조립에 넘긴다 | **미도입** | 1인 사업체는 무료(개인 또는 3인 이하 조직). 4인 이상이 되면 회사 라이선스(자동화 용도 렌더 1건 0.01달러, 월 최소 100달러) |

**왜 Remotion 을 모션 구간에만 쓰나.** 본편 전체를 Remotion 으로 그리면 60초 × 30프레임 = 1,800프레임을 헤드리스 브라우저가 그려야 한다. 3초 인트로는 90프레임이다(30fps 기준 계산). 같은 VM 에 게이트웨이와 대시보드 컨테이너 4개가 함께 도는 상황(T-5)에서 이 차이가 크다. 컷·자막·합성은 ffmpeg 가 이미 운영에서 돌고 있어 새로 짤 이유가 없다.

**왜 ASS 만으로는 안 되나.** ASS 는 글자를 움직일 수 있지만 로고 등장, 도형이 그려지는 제목 카드, 브랜드 색 배경 전환 같은 그래픽 요소는 표현 범위 밖이다. 회장 R-26-4 의 "인트로 아웃트로 같은것도 삽입하고 모션그래픽도 넣고" 는 ASS 의 범위를 넘는다.

**Remotion 을 들이지 않으면(대안).** 인트로·아웃트로를 미리 만든 고정 mp4 로 두고 ffmpeg 가 로고 이미지와 글자를 그 위에 얹는다. 비용은 0원 그대로지만 V-04 "내 브랜드로 만들기" 가 로고 얹기와 배경색 바꾸기 수준으로 줄고, 템플릿마다 움직임을 손으로 다시 만들어야 하며, 미리보기는 고정 mp4 위에 흉내 내는 방식이 되어 T-4 일치 판정이 약해진다.

**PRD 가 거는 제약.** ①모션 구간 렌더도 T-5 VM 전체 상한에 포함한다. ②모션 구간 하나의 길이는 10초 이하(V-04 업로드 제한과 같은 값). ③Remotion 이 쓰는 글꼴은 T-2 서버 설치 목록과 같은 파일이다. ④브랜드 키트 값이 바뀌지 않았으면 이미 렌더한 모션 구간을 다시 쓴다. ⑤회사 라이선스 전환 조건(조직 4인 이상)이 생기면 그 달 안에 비용 표에 올린다.

## 10. 대표 시나리오 (1단계 완료 판정에 쓰는 E2E)

**E2E는 미리 만든 소재 픽스처로 돈다.** 사진 3장, 40초 9:16 나레이션 영상 1개, 로고 1개, 음악 1곡을 고정 파일로 두고 시나리오가 그것을 쓴다. 이미지·영상 생성기(외부, 유료, 524 위험)에 E2E가 매달리지 않게 하기 위해서다. 생성기 연결은 별도 점검(배포 후 점검)이 맡는다.

**시나리오 A. 카드뉴스.** 김민서(38세, 1인 교육·컨설팅 대표, `docs/plan/persona.md`)가 "상담 전에 꼭 묻는 질문 5가지" 를 생성실에서 C 과정 설명형 구조로 고르고, 템플릿 줄에서 추천된 "번호 목록형" 대신 "큰 제목 표지형" 을 골라 7장을 만든다(TP-01, 픽스처 경로에서는 7장 덱을 연다) → 2장 제목을 끌어 위로 옮기고 모서리로 키운다 → 3장 배경을 업로드 사진으로 바꾼다 → 마지막 장에 로고를 얹고 15도 회전 → 1:1 판을 만들어 넘친 글 1개를 줄인다 → 발행실에서 인스타그램(4:5)·X(1:1, 4장 선택)를 고르고 발행 → 두 채널 게시물 주소가 남는다.

**시나리오 B. 영상.** 40초 숏폼 작업물(픽스처) → 대본 두 줄을 지워 컷(6초 감소) → "내 브랜드" 인트로 2초·아웃트로 3초 → 자막 "박스 배경" 프리셋, 핵심 단어 노란 강조 → 제목 글 "아래서 올라오기" → 인트로 뒤 "흐려지며" 전환 → 배경음악, 말소리 구간 자동 낮추기 → 인트로 서랍에서 썸네일 2개를 미리 재생해 보고 하나를 넣은 뒤 "제목 카드" 로 바꾼다(V-16·V-17) → 표지 탭에서 추천 장면 2번을 고르고 표지 글 "박스 배경" 을 얹는다(VC-01·VC-02) → 내보내기 진행 중 발행실로 이동 → 완료 후 릴스·쇼츠·틱톡 발행 → 내보낸 mp4를 내려받아 같은 시각 정지 캡처로 컷·인트로·자막 스타일 확인 → 릴스 게시물 표지에 표지 글이 보이고, 틱톡 표지가 고른 장면 시점이며, 쇼츠 칸에 자동 선택 고지가 있었는지 확인(VC-03).

**시나리오 C. 템플릿 왕복(v1.3.0).** 카톡 대화 9장 덱(픽스처, 숫자·고유명사 포함) → 3장 말풍선 하나를 고침 → "템플릿: 카톡 대화 ▾" → 갤러리에서 "큰 제목 표지형" 비교 → 바꾸기 → 글 보존 검사 통과 확인 → 편집실을 닫았다 다시 연다 → "이전 템플릿으로 돌아가기" → 고친 말풍선이 그대로 있다 → 내보낸 PNG 9장이 바꾸기 전과 같은 글을 담는다(TP-02·TP-03).

**시나리오 D. 글 후보(v1.3.0).** 생성실 글 형식 → A 구조 → 금액 확인 1회 → 채널 4개 × 후보 3개 → 추천을 건드리지 않고 편집실로 → Threads 본문 = 추천 후보 확인 → 10자 고침 → X 탭에서 숫자형 칩을 비교한 뒤 고름 → "원문과 다름" 경고가 없는 것 확인 → 발행실에서 Threads·X 발행 → 게시물 주소 2개(W-01~W-05).

실발행 단계(게시물 주소 확인)는 9444 포트 크롬의 일반회원 계정 "OSMU 홍보대사" 로 한다(§13 결정 2 해소, 회장 허가 범위 "자유롭게 만들고 올려도 돼"). 회장 실계정으로는 실발행하지 않는다.

## 11. 성공 지표와 kill-criteria

**지표는 둘로 나눈다.** 하나로 묶으면 "편집이 불편해서 안 끝낸 것"과 "내보내기가 실패해서 못 낸 것"이 구분되지 않는다.

| **편집 완주율** | 편집실에 들어온(S4) 작업물 | 그중 7일 안에 내보내기를 한 번이라도 **요청한** 작업물 | 편집기가 끝까지 쓸 만한가 |

- (v1.3.0) 원문에 없는 숫자·고유명사가 든 글 후보가 "추천" 배지를 단 채 노출됨(W-02·W-04, BRAIN 윤리 1선 "거짓 정보")
- (v1.0.0 kill ③에서 이동) 회장 dogfood에서 시나리오 A·B를 끝까지 못 가는 결함이 묶음4 출하 뒤 2주 안에 해소되지 않음

**"출하 중단"의 정의.** 해당 묶음의 기능 플래그를 끈다 → 그 기능을 쓰던 작업물에는 "이 기능을 잠시 껐습니다, 사유: ..., 이미 만든 파일은 다시 내보내기를 권합니다" 를 그 자리에 보인다 → 편집 데이터는 지우지 않는다 → 원인 수정 후 플래그를 다시 켠다. 이미 발행된 게시물은 건드리지 않는다.

**kill-criteria (반증 가능, 교체본)**
1. **기한 초과**: 어느 묶음이든 기한의 150%(묶음1 = 1.5주, 묶음2·3 = 3.75주, 묶음4 = 2.25주, 묶음5 = 1.5주)를 넘기면, 그 시점까지 완료 판정을 통과한 요구만 출하하고 남은 요구는 2단계로 넘긴다. 묶음을 붙잡고 늘어지지 않는다.
2. **자유 배치 사용률**: 묶음2 출하 4주 뒤, 편집실에 들어온 **외부** 작업물 중 이동·크기·회전을 한 번이라도 쓴 비율이 15% 미만이면 C-14·C-15(그룹·템플릿 저장)를 멈추고 "템플릿 고르기 + 글 고치기" 중심으로 바꾼다. 외부 작업물이 30건 미만이면 판정을 미루되 **최대 8주**까지만 미룬다. 내부 사용은 이 비율에 넣지 않는다. (unsourced: 첫 실험선)
3. **렌더 건강**: 내보내기 실패율이 2주 연속 10% 초과, **또는** 렌더가 도는 동안 다른 화면 API 응답 p95가 2초 초과이면 모션 2단계(V-08 12종·V-09·V-10 8종)를 멈추고 렌더를 별도 VM으로 분리한다(T-8). (unsourced: 첫 실험선)
4. **(v1.3.0) 글 후보 2·3번째 선택률**: 묶음5 출하 4주 뒤, 외부 고객이 후보를 고른 건(추천을 그대로 둔 것 포함) 중 **추천이 아닌 후보(2·3번째 + 다시 쓰기)가 선택된 비율이 15% 미만**이면 생성 시 후보를 1개(추천)로 줄이고 "다른 각도로 다시 쓰기"(W-06)만 남긴다(Buffer AI Assistant 방식, §12). 외부 선택 50건 미만이면 판정을 미루되 최대 8주. 근거: 후보 3개의 품질이 같고 고객이 위치만 보고 고른다고 해도, 순위 1위 추천은 기대치보다 1.53~1.87배 더 눌린다는 추천 시스템 실측(§12)을 3개 후보 기본 33%에 적용하면 1위 몫은 약 50~62%, 나머지 몫은 약 38~50%다. 2·3번째 몫이 그 3분의 1 아래(15% 미만)라면 고객이 후보를 비교할 가치를 거의 못 느낀다는 뜻이고, 후보 생성 비용(T-10)을 계속 낼 이유가 없다. (15% 선 자체는 첫 실험선, unsourced)
5. **(v1.3.0) 템플릿 고르기 사용률**: 묶음2 출하 4주 뒤, 템플릿 줄이 노출된 외부 카드 작업물 중 **추천이 아닌 템플릿을 고르거나 편집실에서 바꾼 비율이 5% 미만**이면 템플릿 줄을 접힘 기본("템플릿: 큰 제목 표지형 · 바꾸기")으로 바꾸고 사진·글 템플릿 추가 제작(2단계 확대)을 멈춘다. 외부 작업물 30건 미만이면 최대 8주까지 미룬다. 반대로 카톡 대화 선택 비율이 80%를 넘으면 회장 R-27-2 의 우려와 달리 고객이 카톡을 원한다는 신호이므로 추천 규칙 ①(사용 기록)이 제대로 도는지 점검한다. (unsourced: 첫 실험선)

**(v1.3.0) R-27 은 결정 항목을 늘리지 않는다.** 템플릿 6종의 구성, 갤러리 위치, 표지 채널 처리, 글 후보 3개·추천 미리 선택은 모두 화면 배치·흐름이라 추천안으로 확정했다(헌법 §4.3, 실수원장 [false-dichotomy-decision] 재발 방지로 회장 요구와 하나씩 대조했다: §18 R-27 추적표). 돈이 걸린 곳은 글 후보 생성 비용 하나인데, 이것은 새 가격 결정이 아니라 기존 비용 승인 관문(D-014)으로 실행 전에 금액을 보이는 것으로 처리한다. 후보 생성 비용이 1개 생성 대비 2배를 넘는 것으로 실측되면(T-10) 그때 회장께 가격 표시 방식을 올린다.

**결정 1. 영상 모션그래픽 구간에 Remotion 을 들일지 (확인만 필요)**

v1.1.0 은 이 결정을 "ffmpeg + ASS 대 Remotion" 중 하나를 고르는 문제로 물었다. 잘못 세운 질문이었다. ffmpeg 는 영상을 자르고 잇고 합성하는 도구이고, ASS 는 자막 파일 형식이며, Remotion 은 React 코드로 모션그래픽 영상을 만드는 프레임워크다(Remotion 은 내부에 ffmpeg 를 갖고 있다). 셋은 서로 대체하지 않고 나눠 맡는다(§8.3).

- 무엇을: 인트로·아웃트로·움직이는 제목 같은 모션그래픽 **짧은 구간만** Remotion 으로 만들고, 컷·이어붙이기·자막 굽기·나레이션·음악 합성은 지금 운영 중인 ffmpeg 가 계속 맡는 구조를 승인할지.
- 하면(추천): 회장 요구 R-26-4 의 인트로·아웃트로·모션그래픽을 브랜드 로고·색·글꼴이 자동으로 들어간 템플릿으로 낼 수 있다(V-04). 편집 화면에서 인트로 글을 고치면 같은 코드가 바로 재생되고 내보낸 파일도 같은 코드로 만들어져 미리보기와 결과가 맞는다(T-4). 비용은 1인 사업체라 0원이다. 회사 인원이 4인 이상이 되면 회사 라이선스(렌더 1건 0.01달러, 월 최소 100달러)로 바뀐다. 서버 부담은 수 초짜리 구간만 그리므로 본편 전체를 그리는 것보다 작을 것으로 보지만 수치는 미검증이고, 묶음3에서 실측해 VM 전체 동시 렌더 상한 1~2 안에서 함께 센다(T-5).
- 안 하면: 인트로·아웃트로를 미리 만든 고정 영상으로 두고 ffmpeg 가 로고와 글자를 얹는다. 비용 0원은 같지만 "내 브랜드로 만들기" 가 로고 얹기와 배경색 바꾸기 수준으로 줄고, 움직이는 제목 카드와 2단계 카운트업·형광펜 밑줄은 만들기 어렵다.
- 추천: 역할 분담 승인. 근거는 셋이다. ①요구(R-26-4)를 ASS 와 ffmpeg 만으로는 다 채우지 못한다. ②국내 숏폼 자동화 경쟁사 sigmine 이 이미 Remotion 4.0.435 로 렌더하고, Submagic·Typeframes 같은 해외 숏폼 도구도 Remotion 위에서 돈다(§12). ③지금 비용 0원이고, 운영 중인 ffmpeg 는 그대로 쓴다.

### 15.1 Steelman: "Canva를 다시 만드는 것은 1인 회사가 질 수 없는 싸움이다"

가장 강한 반론은 이렇다. Canva·미리캔버스·CapCut은 수백 명이 수년간 만든 편집기다. 우리가 같은 것을 만들면 영원히 그들보다 못한 복제품이 되고, 그 사이 생성 품질·발행 자동화라는 우리 본업이 멈춘다. 차라리 Canva로 내보내기 연결을 붙이고 편집은 남의 도구에 맡기자는 주장이다. 이 반론은 범위에 대해서는 맞다. 그래서 이 문서는 다중 트랙·키프레임·사진 보정·영상 색 보정을 처음부터 버렸고, 요소 종류를 5개, 애니메이션 프리셋을 1단계 4종으로 묶었다. 그러나 결론은 받지 않는다. 고객이 Canva로 나가는 순간 "생성 → 편집 → 채널별 규격 → 발행 → 성과" 한 줄이 끊기고, 발행실은 파일을 다시 받아야 하며, 성과를 다음 생성에 되먹이는 고리도 끊긴다. 회장 R-26의 문장 자체가 "편집실에서 편집하고 플랫폼별로 맞게 발행까지"다. 우리가 이기는 지점은 편집기의 깊이가 아니라 **편집이 발행과 같은 작업물 위에서 이어진다는 것**이고, P-02(내용 공유·배치 분리)와 P-05(내보낸 판이 발행 조건)가 그 차이를 만든다.

### 15.2 Premortem: 석 달 뒤 이 증분이 실패했다면

첫 시나리오는 미리보기 일치가 깨진 경우다. 자유 배치와 회전, 부분 글자 색이 붙은 뒤 내보낸 PNG에서 한글 줄바꿈이 한 글자씩 어긋나고, 김민서가 인스타그램에 올린 뒤에야 제목이 두 줄로 깨진 것을 발견한다. 한 번 겪은 고객은 그 뒤 모든 결과물을 의심하며 Canva로 돌아간다. 대응은 1단계 순서의 첫 항목을 렌더 단일화(T-1)와 자동 비교 테스트(X-02)로 둔 것이고, 운영에서 1건이라도 나오면 출하 중단 가드레일로 걸었다.

두 번째 시나리오는 영상 렌더가 VM을 잡아먹는 경우다. 고객 다섯 명이 동시에 60초 영상을 내보내자 대시보드 전체가 느려지고 생성실 요청이 시간 초과로 끊긴다. 지난 9월 게이트웨이가 CPU 100%로 멈춘 일이 있었던 같은 VM이다. 대응은 내보내기 대기열과 동시 실행 수 제한(T-5), 접수 번호 방식(T-6)이며, 원인 구조도 확인했다. 지금 동시 상한은 컨테이너마다 따로 세서 VM 전체로는 8개가 동시에 돌 수 있다(T-5). 대응은 VM 전체 상한 1~2, 렌더 컨테이너 CPU 상한, 공유 영속 대기열과 순번 표시(T-5·T-6)이며, 묶음1에 동시 5건 부하 실측을 넣는다. 단독 3분·동시 마지막 12분을 못 지키거나 렌더 중 API p95가 2초를 넘으면 Proxmox 호스트에 렌더 전용 VM을 따로 띄워 옮긴다(T-8, 0원, 되돌림 가능). v1.2.0 에서 모션그래픽 구간을 Remotion 으로 그리게 되면서 헤드리스 브라우저 렌더가 새로 들어오므로, 같은 상한이 ffmpeg 와 Remotion 렌더를 함께 세고 묶음3 실측에 Remotion 3초 인트로 렌더 시간·최대 메모리를 넣었다(§8.3).

### 15.3 레드팀 1회: 회의적인 사장님 고객의 공격

"나는 디자이너가 아니다. 빈 캔버스에 요소 30개를 놓을 수 있다는 건 나한테 일이 30개 생긴다는 뜻이다." 유효한 공격이다. 그래서 편집실은 빈 캔버스에서 시작하지 않는다(G-04). 생성실이 만든 완성된 덱이 먼저 들어오고, 사장님이 하는 일은 대개 "글 고치기, 사진 바꾸기, 한두 개 옮기기"다. 자유 배치는 필요할 때만 쓰는 손잡이다. kill 기준이 이 가정을 직접 잰다. 요소 조작을 쓰는 비율이 15% 미만이면 자유 배치 확장을 멈추고 템플릿 고르기 중심으로 돈다.

### 15.3-2 (v1.3.0) Steelman: "후보 3개는 고객에게 일을 세 배로 준다"

가장 강한 반론은 이렇다. 1인 대표는 글을 고르러 오지 않고 끝내러 온다. 채널 4개마다 후보 3개를 읽게 하면 읽을 글이 12개가 되고, 그중 둘은 버려질 글에 돈과 시간을 쓴 것이다. Buffer 가 제안을 1개만 주고 "다시 쓰기" 를 두는 것도 그래서다. 이 반론은 비용 쪽에서는 맞다. 그래서 이 문서는 고르기를 필수 단계로 두지 않았다(추천을 미리 골라 그대로 넘어가면 지금과 같은 일의 양이다, W-02). 후보끼리 한 축(훅 각도)만 다르게 해 비교가 "어느 첫 문장이 내 독자에게 맞나" 하나로 줄도록 했다. 그래도 고객이 2·3번째를 거의 안 고르면 그 비용은 낭비이므로 kill ④ 가 Buffer 방식으로 되돌린다. 반론의 결론(후보를 아예 안 낸다)은 받지 않는다. 회장 제안이고, 훅 각도에 따라 첫 3초 반응이 갈린다는 것이 이 제품의 그로스 가설이며, 그것을 잴 수 있는 가장 싼 방법이 후보를 내고 고른 각도를 기록하는 것(W-07)이기 때문이다.

### 15.3-3 (v1.3.0) Premortem: 석 달 뒤 템플릿 고르기가 실패했다면

첫 시나리오는 템플릿을 바꿨다가 글이 사라진 경우다. 김민서가 카톡 대화 9장을 큰 제목 표지형으로 바꿨는데 7장의 말풍선 하나가 본문 칸 길이를 넘어 잘렸고, 넘침 경고를 못 본 채 인스타그램에 올린 뒤 댓글로 "문장이 끊겼어요" 를 받는다. 대응은 글 보존 검사(T-9)를 바꾸기 확정 조건으로 건 것, 넘친 글은 잘라 내지 않고 넘침 경고(C-13)로 남기는 것, 7일간 이전 템플릿으로 돌아가기(TP-03), 그리고 이 사고 1건이 나오면 출하 중단 가드레일이다.

두 번째 시나리오는 사진·글 템플릿 4종이 "AI 가 만든 티" 가 나서 아무도 안 고르는 경우다. 고객은 결국 카톡 대화만 쓰고 템플릿 줄은 장식이 된다. 대응은 kill ⑤(추천 아닌 템플릿 선택 5% 미만이면 접힘 기본 + 추가 제작 중단)와, 템플릿 4종을 디자인 단계에서 D-2026-09-21-1 품질 기준선(9축 갭표)으로 검수하게 한 것(§17)이다. 카톡 대화가 80% 를 넘으면 그것은 실패가 아니라 고객 선호라는 것도 kill ⑤ 에 적었다.

### 15.4 셀프심문: 이 결론이 틀렸다면 가장 그럴듯한 이유

가장 하중을 받는 가정은 "1단계를 하나로 묶어야 회장 지시가 끝까지 돈다"는 것이다. 틀렸다면 1단계가 너무 커서 몇 주 동안 아무것도 운영에 안 나가고, 회장은 또 "아직도 안 됐냐"를 보게 된다. 반박을 시도하면 이 가정은 절반만 견딘다. 범위는 맞지만 한 번에 내는 것은 틀렸다. 그래서 §9에서 1단계를 **기한이 붙은 묶음**(v1.3.0 기준 5묶음: 1주·2.5주·2.5주·1.5주·1주)으로 쪼갰고, 묶음마다 운영에 나간다. 첫 묶음(내보내기 뼈대 + 표지 사진 실반영 결함 해소)은 1주 안에 회장이 볼 수 있는 변화다. 그래도 늘어지는 경우를 위해 kill ①이 기한 150%에서 남은 요구를 2단계로 넘기게 했다.

v1.3.0 셀프심문: 가장 하중을 받는 새 가정은 "템플릿을 바꿔도 글을 잃지 않게 결정적 규칙으로 옮길 수 있다" 는 것이다. 틀렸다면 카톡 대화 ↔ 사진·글 왕복에서 말풍선 쪼개기·합치기가 원래대로 돌아오지 않는다. 그래서 왕복 결과가 원본과 같아야 한다고 요구하지 않고, **글자 수와 숫자·고유명사 보존**만 확정 조건으로 걸었으며, 배치까지 원래대로 돌려야 하는 경우는 "이전 템플릿으로"(보관된 직전 덱)가 맡게 나눴다(TP-03).

0번 게이트 자문: 매칭 스킬 `document-generate` 를 실제로 호출했다(v1.3.0 개정에도 호출, 조사 우선·정확성 규율 적용, 커밋·README 갱신 단계는 위임 제약상 생략).

## 16. 사업 잠식·시너지

이 증분은 OSMU 내부 편집 기능이다. 회장의 다른 벤처(D-EDU·ZERO-ONE 등)는 OSMU를 자기 콘텐츠 출고 라인으로 쓰므로, D-EDU 카드컨셉13 수준의 카드를 OSMU에서 직접 만들 수 있게 되면 그 벤처들이 별도 편집 도구(Canva 등)에 쓰는 시간이 준다. 잠식 위험은 없다. 그로스 레인의 메타 데모 캠페인(회장 2026-09-16)은 "생성부터 편집, 채널별 발행까지 한 화면에서 도는 모습"이 곧 데모이므로 이 증분의 시나리오 A·B가 캠페인 핵심 자산이 된다. v1.3.0 의 글 후보는 OSMU 자체 계정 운영에도 바로 쓰인다. 훅 각도별 성과(W-07)가 쌓이면 그로스 레인의 훅 실험 데이터가 되고, 다른 벤처(D-EDU 등)가 OSMU 로 글을 낼 때도 같은 데이터가 생긴다. 잠식은 없다.

## 19. 기존 기능과의 관계

빼는 기능은 없다. (v1.3.0) 바뀌는 운영 기능은 두 곳이다: 생성실 카드뉴스 결과물 단추 3개는 템플릿 줄의 주 단추로 합쳐지고 문구는 그대로 쓰인다(TP-01), 발행실 "대문 시점" 초 입력은 편집실 표지 값의 읽기 표시가 된다(VC-04). 편집실 v70의 모든 기능(글 편집기·상한 미터, 카톡 말풍선 툴바 5개, 장 스트립, 영상 대본=컷·타임라인·목소리 선택)은 그대로 두고 그 위에 얹는다. 음악 형식 제거(v70 §5)는 유지한다. 배경음악은 형식이 아니라 영상 편집 안의 레인으로 돌아온다(V-11).

- 생성실(`studio?room=create`, v1.3.0): 구조 초안 A/B/C·그림 결 칩 6종·표지 헤드라인 공식 고르기는 그대로. 카드뉴스 형식에서 구조를 고른 뒤 템플릿 줄(TP-01)이 결과물 단추 위에 붙고, 글 형식에서는 글 만들기 결과가 채널별 후보 3개가 된다(W-01·W-02). 생성실 흐름 정본은 v2.1.0 이다.
- `videos`(영상 작업대)·`images`(에셋 갤러리): 이미지 교체 서랍(C-08)의 "생성된 이미지" 출처. 화면 변경 없음.
- 발행실(`studio?room=publish`): P-03~P-05가 채널 판정에 "비율판 필요", "다시 내보내기 필요" 사유를 더한다. v2.1.0 §5.3 판정표에 들어간다. (v1.3.0) 영상 채널 카드 머리줄의 "대문 시점" 입력이 편집실 표지의 읽기 표시가 되고, TikTok·Shorts 칸에 표지 전달 한계 고지가 붙는다(VC-03·VC-04).
- 학습 정보(`LearningCardWizard`): 브랜드 키트 원천. 로고·색·글꼴 칸이 없으면 기술설계에서 추가 여부를 정한다.
- `channels`·`settings`: 발행실 "계정 미연결" 판정의 해결 단추가 가는 곳. 변경 없음(v2.0.0 소관).
- `inbox`(승인 인박스)·`calendar`(발행 캘린더): 내보내기를 마친 S5 작업물이 들어가는 곳. 발행실 복귀 문맥은 기존 계약 유지, 변경 없음.
- `performance`(성과실): 발행 뒤 S8. 3단계 P-06·댓글 반응 오버레이가 여기서 실제 댓글을 가져온다. 화면 변경 없음.
- `login`·`signup`: 흐름 시작 전 단계, v2.0.0 소관, 변경 없음.

**이 증분과 무관하며 변경 없음(다른 문서·라인 소관):** `blog`, `blog-performance`, `keyword-planner`, `naver-trends`, `google-trends`, `google-analytics`, `search-console`, `search-advisor`(블로그·검색·분석 도구), `operator`, `customers`, `services`(운영자·서비스 전환 화면), `privacy`, `terms`, `data-deletion`(법적 고지·삭제 요청).
