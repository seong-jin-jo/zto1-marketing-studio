## 2026-10-07 self-hosted runner 워크스페이스 격리

운영 VM의 GitHub Actions `GITHUB_WORKSPACE`는 운영 compose 프로젝트 루트이기도 하다. `docker-compose.postagi-4tenants.yml`의 tenant1~4는 이 루트 아래 `config-tenantN`과 `data-tenantN`을 상대경로 bind mount한다. 따라서 비배포 워크플로가 저장소 루트에 기본 checkout하면 actions/checkout의 기본 `clean: true`가 실행하는 `git clean -ffdx`가 운영 원본을 삭제할 수 있다.

적용한 경계는 다음과 같다.

- `ci.yml`: `_ci/src`에 checkout하고, run 기본 디렉터리는 `_ci/src/dashboard`로 둔다. npm cache lockfile과 openclaw 의존성 복사 경로도 이 하위 경로를 사용한다.
- `osmu-db-migrate.yml`: `_ci/migrate-${{ github.run_id }}/src`에 checkout하고, `SOURCE_DIR`과 모든 run 기본 디렉터리를 같은 경로로 둔다. 실행별 source tree가 겹치지 않는다.
- `deploy-marketing.yml`: 운영 출고 경로라 이번 변경에서 수정하지 않았다. 이 워크플로만 루트를 정리한 직후 `~/openclaw-persist`의 config, data, `.env`를 복원한다.
- 무결성 계약: `marketing_runner`를 쓰는 모든 워크플로를 순회한다. deploy 이외의 checkout은 하위 `path`가 필수이고, run working-directory도 checkout 하위여야 한다. 루트 `git clean`과 `rm -rf`는 거절한다.

로컬 임시 디렉터리에서 `_ci/src` 안의 `git clean -ffdx`를 실제 실행했다. child untracked 파일은 삭제됐고, 루트 형제인 `config-tenant2/sentinel`과 `data-tenant2/sentinel`은 보존됐다. 운영 러너 실제 실행, 실행 중 container mount 원본, 운영 데이터 복구 상태는 미검증이다.

### 근본 해결 선택지, 운영 변경이므로 미구현

1. 추천: compose bind mount 원본을 워크스페이스 밖 영속 경로로 옮긴다. 예를 들어 `~/openclaw-persist/tenants/...`를 직접 mount하면 checkout과 운영 데이터 생명주기가 분리된다. 대신 운영 compose 변경, 기존 데이터 이동, container 재생성, rollback 검증이 필요하다.
2. 현재 방식 유지: workspace 하위 bind mount를 유지하고 integrity 계약으로 모든 비배포 workflow를 차단한다. 지금 즉시 안전 경계를 만들 수 있지만, GitHub Actions 밖의 수동 정리 명령이나 검사 범위 밖 도구가 루트를 지우는 잔여 위험이 남는다.
