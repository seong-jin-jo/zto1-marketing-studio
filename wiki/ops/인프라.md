## 2026-10-08 승인 DB 마이그레이션 checkout 권한 오류 교정

운영 승인 뒤 실행한 GitHub Actions run `37751223311`은 `actions/checkout@v4`가 `_ci/migrate-37751223311`을 만들 때 `EACCES`로 실패했다. checkout 뒤 모든 DB 단계가 skipped였으므로 이 실행은 운영 DB를 변경하지 않았다. 서버 SSH로 소유자를 직접 확인하지 못했으므로 확인되지 않은 소유자 원인을 단정하지 않고, 실패 지점은 "runner 프로세스가 `_ci` 아래 run별 새 디렉터리를 만들 수 없음"으로 한정한다.

## 2026-10-07 self-hosted runner 워크스페이스 격리

운영 VM의 GitHub Actions `GITHUB_WORKSPACE`는 운영 compose 프로젝트 루트이기도 하다. `docker-compose.postagi-4tenants.yml`의 tenant1~4는 이 루트 아래 `config-tenantN`과 `data-tenantN`을 상대경로 bind mount한다. 따라서 비배포 워크플로가 저장소 루트에 기본 checkout하면 actions/checkout의 기본 `clean: true`가 실행하는 `git clean -ffdx`가 운영 원본을 삭제할 수 있다.

적용한 경계는 다음과 같다.

- `ci.yml`: `_ci/src`에 checkout하고, run 기본 디렉터리는 `_ci/src/dashboard`로 둔다. npm cache lockfile과 openclaw 의존성 복사 경로도 이 하위 경로를 사용한다.
- `osmu-db-migrate.yml`: 최초에는 `_ci/migrate-${{ github.run_id }}/src`를 썼으나 운영 runner의 새 디렉터리 생성 권한 오류로 실패했다. 2026-10-08부터 host migration 성공 이력이 있는 root child 패턴의 고정 경로 `source-migration`을 사용하고, `SOURCE_DIR`과 모든 run 기본 디렉터리도 같은 경로로 둔다.
- `deploy-marketing.yml`: 운영 출고 경로라 이번 변경에서 수정하지 않았다. 이 워크플로만 루트를 정리한 직후 `~/openclaw-persist`의 config, data, `.env`를 복원한다.
- 무결성 계약: `marketing_runner`를 쓰는 모든 워크플로를 순회한다. deploy 이외의 checkout은 하위 `path`가 필수이고, run working-directory도 checkout 하위여야 한다. 루트 `git clean`과 `rm -rf`는 거절한다.

로컬 임시 디렉터리에서 `_ci/src` 안의 `git clean -ffdx`를 실제 실행했다. child untracked 파일은 삭제됐고, 루트 형제인 `config-tenant2/sentinel`과 `data-tenant2/sentinel`은 보존됐다. 운영 러너 실제 실행, 실행 중 container mount 원본, 운영 데이터 복구 상태는 미검증이다.

### 근본 해결 선택지, 운영 변경이므로 미구현

1. 추천: compose bind mount 원본을 워크스페이스 밖 영속 경로로 옮긴다. 예를 들어 `~/openclaw-persist/tenants/...`를 직접 mount하면 checkout과 운영 데이터 생명주기가 분리된다. 대신 운영 compose 변경, 기존 데이터 이동, container 재생성, rollback 검증이 필요하다.
2. 현재 방식 유지: workspace 하위 bind mount를 유지하고 integrity 계약으로 모든 비배포 workflow를 차단한다. 지금 즉시 안전 경계를 만들 수 있지만, GitHub Actions 밖의 수동 정리 명령이나 검사 범위 밖 도구가 루트를 지우는 잔여 위험이 남는다.

### Higgsfield credential 저장소와 롤백

- 운영 진실원은 dashboard가 쓰는 호스트 `~/.config/higgsfield/credentials.json`이다. GitHub 시크릿은 강제 복구 입력이며 평상시 배포는 파일을 덮어쓰지 않는다.
- dashboard만 경로를 RW로 마운트하고 UID:GID 0:0, 디렉터리 0700, JSON 0600/root를 유지한다. 만료 임박 제품 선갱신, probe, diagnose, force writer는 같은 `.cli.lock.d/lock` 커널 `flock`을 사용한다. 만료가 5분 넘게 남은 생성·조회는 잠금 없이 실행한다. export worker는 이 경로를 마운트하지 않는다.
- 옛 이미지에 lock wrapper가 없으면 먼저 `force_generator_credentials=false`로 새 이미지를 배포하고, 그 뒤 필요할 때만 force 복구한다. access token과 refresh token 쌍이 없는 입력은 거절한다. 살아 있는 credential 교체는 2차 확인이 필요하며, 교체 전 0600 백업을 만들고 계정 확인 실패 시 자동 복원한다.
- 앱 rollback 시에도 RW mount, UID, mode, lock wrapper와 현재 credential 파일은 유지한다. read-only mount나 과거 시크릿 스냅샷으로 되돌리는 것은 장애 원인을 복원하므로 기본 rollback이 아니다.
- 로컬 계약과 선행 컨테이너 경합은 검증했지만 운영 소유권 전환, force 복구, 실제 이미지 생성, rollback rehearsal은 미검증이다.

감시 워크플로는 운영 compose 프로젝트가 놓인 `GITHUB_WORKSPACE`를 checkout·정리하지 않는다. 실행에 필요한 probe와 상태 판정 스크립트 2개만 GitHub Contents API로 `$RUNNER_TEMP`에 받고, 상태 cache도 같은 임시영역에 둔다. Slack webhook이 없거나 전송이 실패해도 판정 상태는 저장되므로 같은 장애 상태의 알림은 자동 재시도되지 않는다. 알림은 best-effort이며, webhook 설정과 첫 운영 장애·복구 수신은 미검증이다.
