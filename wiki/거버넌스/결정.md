# openclaw-auto 결정 원장

## OD-2026-10-09-3 · Higgsfield 서버 전용 OAuth 세션과 단일 갱신 주체

**결정(회장 상시 승인, 컨트롤러 실행)**:
1. 운영 Higgsfield는 맥 로그인과 분리된 서버 전용 OAuth 세션을 쓴다. GitHub 시크릿은 복구 입력일 뿐 현재 자격 증명의 진실원이 아니다.
2. dashboard 컨테이너만 자격 증명 디렉터리를 쓰기 가능으로 마운트한다. runtime UID:GID는 0:0, 디렉터리는 0700, 자격 증명·설정 파일은 0600/root로 유지한다. export worker는 이 경로를 마운트하지 않는다.
3. 제품 API, 상태 탐침, 운영 진단의 자격증명 갱신 구간은 같은 공유 `flock` 잠금을 거친다. 만료가 5분 넘게 남은 생성·조회 명령은 잠금 없이 실행해 동시 처리량을 보존한다. 배포 전 생존 판정은 CLI를 호출하지 않고 만료 메타데이터만 읽는다.
4. `HIGGSFIELD_CREDENTIALS_JSON`은 `force_generator_credentials=true`일 때만 서버 파일에 쓴다. 실행 dashboard의 공유 잠금 아래에서 0600 백업을 만든 뒤 교체하고 계정 검증 실패 시 즉시 복원한다. 살아 있는 자격증명 교체는 별도 2차 확인도 필요하다. access token과 refresh token 쌍이 없으면 기존 파일을 보존한 채 실패한다. 파일이 없거나 만료돼도 force 입력 없이는 자동 복구하지 않는다.
5. 접수 API는 준비 확인과 생성 명령의 실행 예산을 합쳐도 프록시 100초보다 짧아야 한다. 잠금 획득 제한시간은 인증 실패가 아니라 `GENERATOR_BUSY` 503으로 반환하고, 화면은 1초·2초 간격으로 두 번 자동 재시도한 뒤 정확한 실패 문구를 보여준다.
6. 이 결정은 브랜치 초안 `OD-2026-10-09-1`의 시크릿 스냅샷 force 덮어쓰기 방식을 폐기한다. 운영 파일은 회전된 최신 refresh token을 보존하며 검증 가능한 백업·복원 경로 없이 덮어쓰지 않는다.

**이유**: OAuth 갱신 토큰은 갱신 과정에서 회전할 수 있다. 맥과 서버가 스냅샷을 공유하거나 두 프로세스가 같은 옛 토큰으로 동시에 갱신하면 한쪽 갱신이 다른 세션을 무효화한다. 읽기 전용 mount는 새 토큰을 호스트에 남기지 못해 다음 갱신에서 옛 토큰을 재사용하게 만든다.

**근거**: 회장 2026-10-09 서버 전용 세션 결정, GitHub 시크릿 `updated_at=2026-10-09T00:44:12Z`, deploy runs `37809308410`·`37857533639`, `logs/diff/higgsfield-503-20261009/report.md`, Docker bind mount 공식 문서.

## D-2026-10-05-1 · 영상 플랫폼 화면 키와 저장 키를 분리하고 TikTok 실패 원인을 구조화한다

**결정**:
1. 성과실 Shorts·Reels 집계·판정·목록은 `performance-metrics-coverage.ts`의 `storagePlatforms`를 단일 출처로 사용한다. 채널 상세는 저장 제공자 페이지(YouTube·Instagram)로 연결하고 별칭 URL은 정식 URL로 리다이렉트한다.
2. TikTok 공급자 원문은 사용자 화면에 직접 노출하지 않는다. 검증한 코드, 정리한 메시지, `log_id`는 `published_posts.provider_meta.tiktokError`에 구조화하고, `published_posts.error`와 API 응답에는 코드별 고정 한국어 조치 문구를 저장한다.
3. TikTok 공개 범위와 AI 표시 설정은 소유자 선택이다. 심사 전 공개 거절을 발견해도 제품이 `SELF_ONLY`로 자동 변경하지 않는다.
4. TikTok 상태 조회 실패는 실제 게시 실패가 아니다. 인증·권한·모르는 4xx·빈 `status`는 `in_progress`와 pending 기록을 유지하고 진단과 화면 안내만 갱신한다. provider가 명시한 `FAILED`만 영구 실패로 마감해, 이미 게시됐을 수 있는 영상을 사용자가 다시 발행하지 않게 한다.

**이유**: `youtube`·`instagram_reels`는 발행·수집에 필요한 저장 키이고 Shorts·Reels는 사용자가 고르는 화면 축이다. 문자열 일치로 둘을 같은 것으로 취급하면 실제 수집 완료 글이 0건처럼 보인다. TikTok 오류는 사용자 조치와 운영 추적을 동시에 보존해야 하며 어느 한쪽만 남기면 다시 원인을 잃는다.

**근거**: 회장 2026-10-05 운영 지적, `performance-metrics-coverage.ts`, TikTok Direct Post·Get Post Status·API v2 Error Handling 공식 문서, 표적 Vitest 5파일 39건.

## D-2026-10-04-1 · 편집실 v2 내보내기 작업은 PostgreSQL에, 카드는 JSON 요소 모델과 공용 렌더 컴포넌트로

**결정(회장 2026-10-04 "승인. 진행")**:
1. 내보내기 작업과 장별 상태는 기존 PostgreSQL에 표로 저장하고, 렌더 작업자 하나가 `FOR UPDATE SKIP LOCKED`로 가져간다. 공유 파일 볼륨과 외부 큐 서비스는 채택하지 않는다.
2. 카드 장은 글·사진·도형·스티커·로고 요소의 JSON 배열(좌표·크기·회전·층·서식)을 정본으로 저장하고, 편집 화면(접근 가능한 DOM)과 서버 PNG 렌더가 같은 React 장 컴포넌트를 쓴다. 캔버스 렌더러 확대와 Fabric·Konva 도입은 채택하지 않는다.
3. 자유 배치 발행 차단은 저장 초안을 식별하는 `draft_id`가 있는 경로에 적용한다. `draft_id` 없는 직접 발행은 자유 배치 초안과 연결할 근거가 없으므로 이 결정의 차단 범위 밖이다.

**이유**: 재시작 뒤에도 진행률과 실패 장 재시도가 살아 있어야 하고(PRD v1.3 묶음1), 화면과 결과 PNG가 어긋나지 않아야 한다. 테넌트 경계와 트랜잭션을 기존 DB에서 재사용해 추가 비용이 없다. 한글 직접 입력과 접근성은 DOM 편집이 유리하다.

**근거**: docs/eng/editroom-v2/design.md "합의 전 확정 금지 항목", gap-matrix.md(있음 30, 부분 15, 없음 43), Remotion 공식 문서의 동일 입력 원칙.

## OD-2026-09-09-1 · 구조 초안 생성이 프록시 제한 시간을 넘는다 (미결)

**왜 지금 못 고치나**: 안전한 해법은 서버가 요청을 받는 즉시 그 요청을 장부에 예약해 두고,

3. **생성 시간을 줄인다.** 프롬프트와 모델 설정을 줄여 제한 시간 안에 끝낸다. 가장 싸지만
   품질이 걸리고 언젠가 다시 넘는다.

**하면**: 글 생성이 끊겨도 결과를 잃지 않는다. **안 하면**: 오래 걸리는 생성은 계속 실패로
끝나고, 그때마다 비용은 나간다.

**추천**: 1번. 2번의 이득 대부분을 훨씬 적은 변경으로 가져온다.

## D-2026-09-21-1 콘텐츠 품질 기준선 = 벤치마크 v1, 로드맵 2·4·8주 승인 (회장 확정)

**회장 2026-09-21 원문**: "생성실에서 생성한 컨텐츠 퀄리티는 왜 개쓰레기수준이고 편집은 한단계 더 나아가서 ux가 쓰레기수준이네 ... 니가 생각했을때 이정도로 만들어야겠다는 컨텐츠 레퍼런스 가져와봐. 영상에서 시청자 댓글 반응같은거 삽입하는거아냐? ... 카드뉴스는 디에듀에서 작업한 D-100, 90, 80 카드뉴스 편집같은거 참고하고" → 벤치마크 문서 제시 후 "승인하니까 너가 다해."

**결정**:
1. 생성실·편집실 품질의 기준선은 `docs/design/osmu-content-quality-benchmark-v1-claude-opus.html`(PR 65) 이다. 기준 실물 1번 = D-EDU 카드컨셉13 "수능 100일" 카드(표지 실사 + 후킹 3줄 + 카톡 말풍선 대화 + 댓글 CTA, 11장).
2. 9축 갭표(후킹 표지·실사 배경·말풍선 대화·타이포 위계·브랜드 시그니처·장수·댓글 CTA·숏폼 댓글 반응·재생 미리보기)를 QA 게이트로 쓴다. "네 방이 이어지는가"만 보는 QA 는 품질 판정이 아니다.
3. 로드맵 승인: 1단계 2주(D-EDU 03c 말풍선 편집도구 이식·9장 덱·훅 3공식+CTA 강제·영상 재생·품질 게이트) → 2단계 4주(실사 배경 레이어·위계·워터마크) → 3단계 8주(성과실 실제 댓글을 끌어오는 댓글 반응 오버레이).
4. 표지 실사 배경 기본값 = 추천안 A: 브랜드 사진 → 업로드 → 생성(비용 승인 관문) 순, 비용 0 으로 시작. (오케스트레이터 판정, 회장 회수 가능)

**함께 발견된 운영 결함(별건)**: 운영 이미지 생성기(Higgsfield) 자격증명이 죽어 생성실이 무료 글자 카드만 내고 있었다. 배포 시크릿 갱신은 회장 명령 실행 대기.

## D-2026-09-09-1 편집실은 직접 편집이 기본이고 AI 는 보조다 (회장 확정)

**충돌 지점**: 사업계획 v1.0 §3.2(506행)는 이렇게 적혀 있다.
"편집실도 모델을 씁니다. 자막을 직접 타이핑하게 하면 우리 타깃에게는 그것도 일입니다.
말로 시키면 우리가 정리해 값을 바꿉니다." 기술 과제 표(523행)도 "말로 시키는 편집 /
손 편집 없이 원하는 결과를 내야 합니다" 로 못 박았다. 즉 **손 편집을 피할 것**이 승인된 방향이었다.

**회장 2026-09-09 지시**: "편집실에서는 ai 요청안하고 직접 코드기반으로 수정할수있께 하는건데,
AI 챗봇에서는 '자막에서 어투 이렇게 바꿔줘' 이렇게 요청할수도있는거고."

**판정**: 뒤집는 것이 아니라 **순서를 바꾸는 것**이다. 사업계획은 AI 편집만 두었고, 회장은
직접 편집을 기본에 놓고 AI 를 보조로 남기라고 했다. 둘 다 있어야 한다.

**근거가 회장 쪽에 선다**:
1. 사업계획 §3.2 기술 과제 표가 스스로 "편집실 / 미리보기와 최종 일치 / 다르면 편집실
   신뢰가 무너집니다" 를 최우선 과제로 적었다. 말로 시키는 편집은 이 일치를 보장하기
   어렵다. 모델이 해석한 결과가 미리보기와 어긋나면 그 신뢰가 먼저 깨진다.
2. 우리 팀은 이미 직접 편집 도구를 만들어 쓰고 있다(D-EDU 카드컨셉13 03c-편집도구-통합).
   덱 전환, 원문 대조, 카드 안 문장 직접 편집, 슬라이드 순서 이동, 커버·본문·CTA 역할
   구분, 전체 PNG 내보내기. 검증된 자산을 두고 모델 왕복으로 대체할 이유가 없다.
3. 비용. §4장이 편집실 모델 왕복을 원가에 넣었다. 직접 편집이 기본이 되면 그 왕복이
   줄어 원가가 내려간다. 회장 지시가 사업계획의 수익 구조를 해치지 않고 오히려 돕는다.

**결정 (2026-09-09 회장 정정 반영)**: 둘 중 하나를 고르는 문제가 아니다. **두 길이 다 열려 있어야 한다.**

회장 정정 원문: "편집에서는 AI 챗봇에서는 말로 편집할 수도 있는데 직접 문구 수정이나
드래그앤 드롭정도는 할수있는거지. 프롬프팅보다 편하니까."

- **직접 조작**: 문구 수정과 드래그앤드롭 같은 **작고 정확한 변경**. 여기서는 프롬프트를
  쓰는 것이 오히려 느리고 부정확하다. 글자 하나 고치려고 문장을 지어내는 것은 일이다.
- **AI 챗봇**: "자막 어투를 이렇게 바꿔줘" 같은 **여러 곳에 걸친 일괄 변경**. 손으로 하면
  스무 번 반복해야 하는 것을 한 번에 시킨다.

즉 기준은 "기본이냐 보조냐" 가 아니라 **변경의 크기와 종류**다. 한 곳을 정확히 바꾸는 것은
손이 빠르고, 여러 곳을 같은 규칙으로 바꾸는 것은 말이 빠르다. 편집실은 둘 다 준다.

앞선 판정에서 "직접 편집이 기본, AI 는 보조" 라고 서열을 매겼는데 그것이 틀렸다.
서열이 아니라 **역할 분담**이다.

사업계획 §3.2 의 "손 편집 없이" 는 이 결정에 맞춰 다음 개정 때 고친다.
**사업계획 본문을 아직 안 고쳤다는 사실을 여기 남긴다**(문서와 실물이 어긋난 채로 두지 않는다).

**적용 대상**: 요청 원장 R-1-1 부터 R-1-8.


이번 이관에서 기존 별도 미결 원장은 확인되지 않았다.

# ADR-007 — 조용한 실패 금지: 못 하면 이유를 말하고 빠져나갈 길을 준다

**Status**: Accepted (2026-09-06)

## 맥락

2026-09-05 회장 계정으로 네 방을 직접 눌러 본 결과, 같은 결함이 여섯 곳에서 나왔다.
눌러도 아무 일이 없고 이유도 말하지 않는 것이다. 화면은 멀쩡한데 동작만 없으니
사용자에게는 전부 고장이다. 구체적으로는 다음과 같았다.

- 생성실 초안 만들기가 선행 조건 미충족 시 조용히 비활성
- 발행실 발행이 본문 없을 때 요청도 알림도 없이 반환
- 연결이 끊긴 채널이 발행 대상에 그대로 포함
- 승인 큐에 없는 초안을 내부 기록 실패로 오판해 재발행 차단
- 성과 수집이 제공자 거절을 건너뛰고 성공으로 종료
- 서버가 실패 사유를 예외째 버려 로그에 아무것도 안 남음

## 결정

1. **주 동작 단추를 조용히 비활성으로 두지 않는다.** 누를 수 있게 두고, 무엇이 없어서
   못 하는지 그 자리에서 말한다. 통상적인 페이지 이동 화살표는 예외다.
2. **조용한 반환을 금지한다.** 함수가 아무 일도 하지 않고 끝나면 반드시 이유를 알린다.
3. **막기만 하고 길을 안 주지 않는다.** 재발행 금지 같은 보호 장치에는 그 상태를 닫는
   조치를 함께 준다.
4. **실패 사유를 버리지 않는다.** 예외를 삼키는 자리마다 사유를 로그로 남긴다.
   자격증명 값은 남기지 않는다.
5. **기다리면 되는 것과 조치가 필요한 것을 다른 말로 적는다.** 미수집과 측정 불가를
   같은 말로 쓰면 사용자는 무한정 기다린다.

## 결과

- 여섯 건 모두 고치기 전 코드에서 실패하는 회귀 테스트를 붙였다.
- 관련: `docs/qa/osmu-전체흐름-QA-2026-09-05.md`

# ADR-006 — 심사 전 소셜 연결의 한시 절차는 UI가 안내하고, App Review 통과가 그것을 없앤다

**Status**: Accepted (2026-08-31)

## 맥락

회장이 지적했다. "j.the.great.investor 는 일반유저인데 쟤가 스레드 들어가서 초대 수락하는
과정이 필요해? 만약 그게 필수라면 우리 UI에서 접속링크라도 자연스러운 UX로 가야할것같은데."

지적이 맞다. ADR-004 가 정한 제품 흐름은 고객이 소셜 로그인만 하면 되는 것이다.
테스터 등록과 초대 수락은 **Meta App Review 통과 전에만 존재하는 한시 절차**다.
이것을 제품의 정상 흐름처럼 말하거나 화면 없이 방치하면 두 가지가 동시에 잘못된다.
고객은 막힌 채로 남고, 우리는 없어질 절차를 제품 사양으로 착각한다.

## 결정

1. **한시 절차는 제품 사양이 아니다.** 문서와 보고에서 이것을 정상 흐름으로 서술하지 않는다.
   반드시 "심사 전 한시" 라는 조건을 붙인다.
2. **그 기간 동안은 화면이 끝까지 안내한다.** 연결 화면이 무엇을 눌러야 하는지와
   바깥 링크를 함께 준다. 문장으로만 설명하고 사용자를 방치하지 않는다.
3. **안내는 서버 판정에 따라 저절로 사라진다.** 심사 통과 뒤 화면에 남을 수 있는 경로를
   만들지 않는다. 남으면 존재하지 않는 절차를 고객에게 시키는 결함이다.
4. **연결 단추를 막지 않는다.** 이미 수락한 사람은 안내와 무관하게 바로 연결한다.
5. **App Review 통과를 이 문제의 종결로 둔다.** 안내 UX 는 그때까지의 임시 대책이지
   목표가 아니다.

## 결과

- 이 절차가 필요한 provider: Threads, Instagram, Facebook. 심사 전에만 해당한다.
- 초대 수락 위치: Threads 는 웹사이트 권한의 초대 탭, Instagram 은 프로필의 앱 및 웹사이트.
- 관련: ADR-004(소셜 연결 = OAuth + App Review),
  `wiki/5-hubs/hub-eng/architecture/system-architecture.md` 플랫폼 권한 절.

# ADR-005: 제품명 OSMU(오스무) 확정 · 계정 브랜드 = 콘텐츠 공장 "OSMU 팩토리" (사장님 done-for-you)

# ADR-004 — 고객 소셜 연결: OAuth "연결" + App Review (비번 수집 금지)

**상태**: accepted · **날짜**: 2026-06-29

## 맥락
고객 온보딩에서 가장 어려운 구간 = Meta(Facebook/Instagram/Threads) 앱·토큰 셋업.
"고객한테 Meta 앱·IG/Threads 계정 비번 등 계정정보를 받아 에이전트가 권한·API를 자동 설정하면
편하지 않을까"라는 아이디어가 나왔다(에이전트가 우리 자체 계정 셋업을 브라우저로 운전 가능함을 보고).

## 결정
**고객 비밀번호를 받거나 저장하지 않는다. 고객 소셜 연결은 OAuth "연결" 플로우 + App Review로 한다.**

- 고객은 **"Instagram/Facebook 연결" 버튼** 클릭 → Meta 공식 OAuth 동의 → 우리는 **access/refresh
  토큰만** 수령(비번은 절대 안 받음). 토큰은 `OSMU_SECRET_KEY`로 암호화 저장, 갱신은 우리가.
- 임의 고객 계정에 *대신 발행*하려면 앱이 **App Review**로 발행/인사이트 권한 고급 액세스를 받는다
  (자기 소유 테스터 계정은 review 없이 동작 — 내부 5브랜드는 테스터 방식).
- 이는 앞서 정한 per-tenant "Google 연결"·GA4/슬랙 "플랫폼이 인터페이스" 모델과 동일 계보.

## 왜 비번 수집은 안 되는가 (Why)
1. **치명적 책임** — 고객 소셜 비번 저장 = 한 번 유출되면 전 고객 계정 탈취, 법적·평판 재앙.
2. **Meta ToS 위반** — 비번 기반 자동 로그인은 플랫폼 정책 위반 → 앱·계정 정지.
3. **기술적으로 불안정** — 2FA·캡차·동적 UI로 자동화가 깨짐. Meta가 봇 로그인을 능동 차단.
4. OAuth는 이 셋을 다 푼다 — 비번 안 받고, 정책 준수, 토큰 갱신으로 안정.

## 에이전트 브라우저 자동화의 자리
GStack 브라우저로 Meta 콘솔을 운전하는 건 **우리 자신의 계정 셋업(우리 세션, 일회성 내부 작업)에만**
쓴다. **고객 온보딩 메커니즘으로는 쓰지 않는다**(고객 세션·비번을 우리가 운전 = 위 1~3 위반).

## How to apply
- 상품화 빌드: 채널 Settings에 "Instagram/Facebook/Threads 연결"(OAuth) 버튼 → 콜백 토큰 저장(per-tenant
  integrations) → publish/insights는 저장된 토큰으로. (per-tenant OAuth 연결 빌드 = 기존 백로그.)
- 내부 5브랜드(지금): 우리 앱에 각 계정 테스터 추가 + 토큰 발급(에이전트 브라우저로 우리가 운전 가능).
- 관련: [[../../4-reference/brand-grounding]], ADR-003(pricing), `wiki/3-operations/session-state.md` Meta 셋업.

## 중앙 개발자 앱 credential 운영 (2026-07-28 보강)

- 고객별 `channel_accounts` access/refresh token과 운영자의 중앙 OAuth App ID/Secret은 다른
  보안 경계다. 전자는 tenant 소유, 후자는 모든 tenant의 OAuth 진입에 쓰는 전역 인프라다.
- 운영자는 Admin의 provider 카드에서 callback·공식 콘솔/문서·필수 필드·설정 단계를 확인하고,
  중앙 값을 전체 세트 단위로 등록/교체한다. 저장은 `oauth_app_credentials`에 각 필드별
  pgcrypto 암호화로만 한다.
- 기본 조회는 source(DB/env), 설정 여부, 마스킹 값, 갱신시각만 반환한다. 원문은 정확한 운영자
  Bearer를 다시 요구하는 explicit reveal에서만 no-store 응답으로 반환하고 30초 뒤 UI 메모리에서
  지운다. update/reveal은 `oauth_credential_audit`에 secret 없이 기록한다.
- 기존 운영 환경변수 원문을 별도 HTTP 응답으로 직접 덤프하지 않는다. Admin의 단일
  `원문 확인` 요청이 env 출처의 완전한 provider 세트를 `oauth_app_credentials`에 암호화 INSERT한
  뒤, **같은 DB 트랜잭션 안에서 DB 행을 다시 복호화해 reveal**한다. `import`와 `reveal` 감사 행도
  같은 트랜잭션에 secret 없이 기록한다. 별도 가져오기 버튼은 두지 않는다.
- INSERT는 `ON CONFLICT DO NOTHING`을 유지한다. 요청 사이에 기존 DB 행이 발견되거나 새로 생기면
  env로 덮어쓰지 않고 잠근 DB 행을 정본으로 reveal한다. env 일부 누락, DB·암호화 키 장애,
  불완전한 DB 행은 아무 필드도 혼합하지 않고 fail-closed한다. 성공 응답 뒤 metadata를 즉시
  새로고침해 source DB·준비 상태를 표시한다.
- 런타임은 `resolveOAuthCredentialSet()`만 사용한다. DB 완전 세트 우선 → DB 행이 없으면 기존 env
  완전 세트 fallback → DB 일부만 있으면 env와 섞지 않고 fail-closed다.
- 2026-07-26의 “Admin은 secret 이름/준비상태만 표시하고 원문 입력을 받지 않는다” 운영 결정은
  회장의 2026-07-28 명시 지시로 이 절에서 대체됐다. 고객 UI/tenant token에는 중앙 입력·조회
  endpoint를 노출하지 않는 원칙은 유지한다.

보안 벤치마크:
- OWASP Secrets Management Cheat Sheet의 최소권한, 암호화 저장, secret 비로깅, lifecycle 감사
  원칙을 차용했다:
  https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html
- 민감 응답 캐시 방지는 OWASP REST Security Cheat Sheet의 `Cache-Control: no-store`를 적용했다:
  https://cheatsheetseries.owasp.org/cheatsheets/REST_Security_Cheat_Sheet.html
- 차별화: env secret을 브라우저로 먼저 reveal한 뒤 재전송하지 않고, 단일 운영자 요청·단일 DB
  트랜잭션에서 provider 전체 세트를 암호화 DB로 이동한 다음 DB 값을 reveal해 HTTP 노출면과
  필드 혼합 가능성을 함께 제거했다.

## 계정 전환·provider 세션 경계 (2026-07-24 보강)

- 우리 대시보드 origin은 Meta·Google·X·TikTok 등 **다른 origin이 소유한 로그인 쿠키를 삭제할 수 없다**.
  따라서 “다른 계정 연결”을 누른 것만으로 provider 로그아웃이 됐다고 주장하지 않는다.
- 지원되지 않거나 공식 문서에 없는 `force_authentication`·자동 로그아웃 파라미터를 추측해 붙이지 않는다.
  Meta 계열은 Meta Accounts Center, X/TikTok은 각 계정 설정, YouTube는 Google 앱 연결 관리 화면을
  `noopener noreferrer` 새 탭으로 열어 사용자가 계정/세션을 직접 확인한 뒤 재연결하게 한다.
- Google/YouTube OAuth는 공식 `prompt=consent select_account`를 유지해 연결할 때 계정 선택 화면을 요청한다.
  이 provider 지원 동작과 우리 origin에서 third-party 세션을 삭제할 수 없다는 경계는 동시에 성립한다.
- UI의 약속은 “관리 화면을 연다 → 사용자가 전환/로그아웃한다 → 돌아와 OAuth 연결을 다시 누른다”까지다.
  실제 provider 세션 변경이나 callback 성공은 관찰 전까지 미검증이다.
- 2026-07-30 재확인에서도 Meta의 Threads Authorization Window와 Instagram Login 공식 문서에는
  Google `prompt=select_account`·TikTok `disable_auto_auth`에 대응하는 계정 선택 파라미터가
  문서화돼 있지 않았다. 따라서 Threads·Instagram 연결 버튼 근처에는 각각
  `threads.net`·`instagram.com`에서 먼저 로그아웃하라는 안내와 Meta 계정 센터 링크를 제공한다.
- identity 경계는 path와 세션을 함께 본다. `/operator*`에서는 의도적인 운영자 토큰을 Supabase
  세션보다 우선한다. 고객 로그인/고객 화면에서 Supabase 세션이 확립되면 잔존 운영자 토큰 대신
  고객 JWT를 승격하며, 운영자↔고객·고객 A↔고객 B 전환과 로그아웃 때 `active_workspace`를 비운다.
- path가 바뀌거나 AuthGate가 unmount된 뒤 완료된 Supabase `getSession()` 결과와 그 run의
  `onAuthStateChange` callback은 폐기한다. 이전 customer path의 비동기 초기화가
  `/operator*`에 도착해 운영자 토큰을 고객 JWT로 교체하거나 뒤이은 `SIGNED_OUT`으로 지우면
  위 identity 우선순위가 순서에 따라 뒤집히기 때문이다.
- `/api/connect/{provider}`와 `/api/connect/readiness`는 고객 JWT가 확정한 tenant와 쿼리
  `tenant_id`가 다르면 JWT tenant를 계속 사용하면서 `oauth_connect_tenant_mismatch` 사실만
  구조 로그로 남긴다. tenant id·Bearer·secret 값은 로그에 포함하지 않는다.

## 권한 부여 메커니즘 — 테스터(개발) vs App Review(상품화)
"고객 로그인만 하면 우리가 모든 세팅" = 가능. 단 메커니즘 구분:
- **개발 모드(지금, 내부 5브랜드)**: 각 계정을 앱에 테스터 초대 + 그 계정에서 수락(수동, 자기 계정). 50명 한계.
- **상품화(외부 고객)**: 앱 **App Review 1회** 통과 → 누구나 OAuth "연결" → **Meta 동의 화면에서 권한
  (content_publish·insights 등) 승인** → 우리가 토큰+권한 수령. **테스터 등록·웹사이트권한 수락·콘솔 작업 0.**
  권한 부여는 OAuth 동의가 처리한다(콘솔 자동운전 불필요·금지).
- 상품화 마일스톤 = App Review 준비(privacy policy URL + 이용사례 데모 영상 + 검수 제출).

## 토큰 내구성 계약 (2026-08-14 보강)

- Instagram·Threads는 authorization code로 받은 단기 토큰을 반드시 provider 장기 토큰으로 교환한 뒤 저장한다. 장기 교환 실패 시 단기 토큰 폴백은 금지한다.
- Facebook은 단기 user token, 장기 user token, `/me/accounts` page token 순서를 전부 통과해야 저장한다. 장기 교환이 실패하면 page token 조회로 진행하지 않는다.
- provider가 반환한 `expires_in`은 callback 시점의 절대시각으로 변환해 `channel_accounts.token_expires_at`에 저장한다. access token과 refresh token은 각각 `secret_enc`, `refresh_enc`에 암호화한다.
- Threads·Instagram·X·YouTube는 저장 전 실제 계정 조회로 신원을 확인한다. 실패, 타임아웃, ID 누락을 토큰 교환 응답 ID로 덮지 않고 callback을 실패시켜 `active` 오판을 막는다.
- 연결 판정은 status만 보지 않고 만료시각과 암호화 refresh token 유무를 함께 본다. Meta 장기 토큰 계정이 `active`여도 만료시각이 없으면 `reconnect`다.
- YouTube refresh는 기존 `refresh_enc` 경로를 유지하고 새 access token의 `expires_in`으로 만료시각도 갱신한다. Threads·Instagram의 provider refresh endpoint 자동 호출은 아직 미구현이므로 만료 후에는 재연결이 필요하다.

# ADR-003: Dual-Wiki Moat + Retention-Aligned Hybrid Pricing for Solid AI SaaS

**Date**: 2026-06-18
**Status**: Proposed (following gstack review)
**Context**: After deep 2026 benchmarking (Opus/Munch/Pictory pricing & 20-40% discard, ChartMogul/Optifai NRR data by ACV, market CAGRs, Obsidian vs Notion for AI teams, gstack velocity). Targeting 1,000+ paying subscribers at ₩100k–200k/mo (≈$80–160 USD) with >110% NRR.

## Problem
- Existing shorts/video tools (Opus dominant) suffer high discard (20-40%), video-only focus, unpredictable credit pricing, and billing friction → poor retention at low ACV.
- Text AI tools (Jasper/Copy) are shallow on video + real multi-channel orchestration.
- AI-native SaaS shows collapsing retention at low prices: 32% NRR for sub-$50/mo plans, 61% for $50-249, 85% only above $250 (ChartMogul 2026).
- Internal knowledge is fragmented without a living "Company Brain" → slow iteration and risk of inconsistent decisions as we scale.
- Pure subscription or pure credit models fail to balance predictability for lean startups with value capture from heavy users.

## Decision
Adopt a **Dual-Wiki Knowledge Moat** combined with **Hybrid Base + Usage Pricing** as the core foundation for v4.0 SaaS:

1. **Dual-Wiki Moat**:
   - **Tenant Brand Wiki** (`wiki_docs`): Facts + brand knowledge injected at generation time for accuracy and on-brand output (anti-hallucination).
   - **Project Wiki** (`wiki/`): Obsidian-style local Markdown + Git as internal "Company Brain" for gstack/LLM agents, decisions, benchmarking, architecture. Compounds via /learn + insights.

2. **Pricing Model (target ₩100k–200k/mo)**:
   - **Base Subscription** (predictable floor):
     - Starter: ~₩80-100k — 3 channels, basic automation, limited shorts (50/mo), standard models.
     - Pro: ~₩150-200k — Unlimited channels, full Shorts Factory + insights, priority models, A/B, deeper wiki usage.
     - Team/Agency: Custom — multi-workspace, white-label, API, custom extensions.
   - **Usage Add-ons** (expansion):
     - Per extra 1,000 generations or per 10 shorts minutes.
     - Priority processing / advanced video models.
   - Goal: Land most customers in mid-tier ($50-250 equivalent) for 61%+ NRR base, drive expansion to >110% NRR overall.

3. **Execution Principles**:
   - Always benchmark (this page + reference/benchmarking.md) before pricing or moat changes.
   - Use gstack procedures (office-hours → plan reviews → autoplan) for all major SaaS work.
   - Instrument viral_signals + performance → feed back into prompts/styles + wiki.

## Rationale (from 2026 Deep Benchmark)
- **Retention Data**: Low-ACV pure credit (Opus-style) leads to 32% NRR. Hybrids win because base gives predictability for startup budgets while usage captures success. Mid-tier + expansion path is the only viable route to 1000+ subs with healthy NRR.
- **Competitor Gaps**: Opus ~20-40% discard + no facts grounding + billing complaints. Our wiki facts + agentic multi-channel directly attacks this. Project wiki + gstack gives internal velocity moat competitors can't easily copy.
- **Wiki as Moat**: Local Markdown (Obsidian pattern) wins for AI agents and compounding knowledge (Garry gbrain / Karpathy patterns). Tenant wiki solves product accuracy; project wiki solves dev speed. Dual setup is hard to replicate.
- **Market Timing**: AI content tools growing fast (13-32%+ CAGRs in segments). Vertical SaaS with strong data/knowledge flywheels commands premiums. gstack velocity (810x benchmark) lets us iterate faster than closed tools.
- Aligns with "pay for outcomes" (hours saved + viral posts) while keeping base affordable.

## Trade-offs
- More complex billing/usage tracking than pure sub or pure credit (mitigated by phased rollout).
- Requires strong instrumentation of insights loop early.
- Higher initial ACV target means we must deliver clear ROI (quality + time saved) from day one.
- Separating two wikis adds minor mental model load (but prevents confusion long-term).

## Consequences
- **Positive**:
  - Defensible moat: knowledge flywheel + data loop + velocity.
  - Path to >110% NRR and sustainable 1000+ subs.
  - Clear differentiation vs Opus (facts + multi-channel) and Jasper (full automation + shorts).
- **Immediate Next (gstack-enforced)**:
  - Deep wiki reflection of pricing + moat first (this ADR + vision.md + benchmarking.md).
  - Run full gstack /office-hours → reviews → /autoplan before any code.
  - Then implement usage tracking + shorts grounding with discipline (read files, plan comments, verify).
  - Update roadmap and learnings.
- All future pricing experiments or changes must follow gstack procedures and be recorded here.
- Re-benchmark quarterly or before any pricing change.

**gstack Process Note (2026-06-18 follow-up)**: Initial implementation was premature. Reverted to proper flow: office-hours + CEO/Eng review → deepened wiki reflection → concrete plan before further code. See learnings for details.

- codex 계열은 프롬프트를 파일 경로로 받으므로 훅이 그 파일 내용을 읽어 검사한다.
- 조사·판정 전용 판("제품 코드를 고치지 마라", "판정 전용" 등)은 면제한다.
- 우회 `DELEGATION_GOV_OK=1`.
- 동작 확인: 근거 없는 프롬프트는 차단 메시지 출력, ADR 참조 있는 프롬프트는 통과.

**남은 재발 위험(정직하게 적는다)**:
1. 훅은 **참조 문자열이 있는지**만 본다. 워커가 실제로 읽었는지는 못 본다.
   → 회수 시 컨트롤러가 산출물에 ADR 인용이 있는지 확인해 보완한다.
2. **관련 ADR 을 잘못 고르면** 훅은 통과한다. 주제와 무관한 ADR 을 붙여도 막지 못한다.
3. 우회 변수로 언제든 넘어갈 수 있다. 우회 사용은 실수 원장에 남긴다.


## 2026-08-31 Meta App Review 를 상품화 마일스톤으로 즉시 착수한다

**회장 지적 원문**: "소셜로그인하면 로그인한 유저가 따로 API발급 없이 바로 자동화할 수 있다는게
우리가 사수한 간편성 아니었냐? 클릭클릭하다 API 발급? 돌았어?"

**판정: 회장 말이 맞고, ADR-004 가 이미 그렇게 정해 놨다. 실행만 안 됐다.**
고객은 API 를 발급받지 않는다. 우리 앱 하나가 App Review 를 통과하면
고객은 OAuth 동의 화면에서 권한을 승인하는 것으로 끝난다.

**지금 테스터 등록이 필요한 이유**: 우리 앱이 아직 심사 전이라 개발 모드이기 때문이다.
개발 모드는 테스터로 등록된 계정만 연결된다. 50명 한계.

**결정**: App Review 제출 준비를 즉시 착수한다. codex `osmu-appreview0831` 에 발주.
- 권한별 제출 요구사항 공식 문서 조사
- privacy policy 와 terms 페이지가 Meta 요구를 충족하는지 대조하고 보강
- 데이터 삭제 요청 경로 확보
- 화면 녹화 대본과 영문 이용 사례 문안
- 지금 당장의 우회로(테스터 등록) 정확한 클릭 경로

**변하지 않는 제약**: **Meta 콘솔 자동 조작 금지.** ADR-004 에 명시돼 있고
2026-07-01 에 콘솔 자동 운전으로 개발자 계정이 플래그당한 실사고가 있다.
콘솔 조작과 제출 버튼은 회장이 직접 한다. 세션은 제출물을 만드는 데까지다.

## 2026-08-31 콘텐츠 생성에 실제 LLM 을 지금 붙인다

**회장 결정 원문**: "첫째. 지금 당장 붙여야지"

**배경**: 생성이 LLM 을 한 번도 부르지 않고 문자열 템플릿이었다.
`service.ts buildCandidates()` 가 A/B/C 를 하드코딩 배열로 만들고
`derivation.ts` 도 템플릿, 영상은 `asset_url: "pending:render"` 고정.
네 방 전체가 이 공백 위에 얹혀 있었다.

**결정**: 다른 UX 개선보다 우선한다. codex `osmu-llm0831` 에 발주(2026-08-31 03:28).

**못 박은 제약**:
- LLM 실패 시 템플릿으로 조용히 대체 금지. 화면에 왜 안 되는지 정확히 말한다.
  되는 척하는 UI 가 이 제품이 신뢰를 잃은 이유다.
- 무료 재생성 몫(R27)과 파생 견적 선표시 계약을 깨지 않는다.
- LLM 호출 횟수와 토큰을 기록한다. 기록 없이 돈을 태우지 않는다.
- 타임아웃과 재시도 상한을 둔다.
- 모델명을 코드에 박지 않는다. 설정으로 뺀다.
